# 第 6 课　让 AI 操作 GitHub：你来验收

**这一课学完：** 你把前五课的规矩写给 AI，让它开分支、提交、开 PR、修 CI；你只看几处关键的地方，就能判断它交来的东西能不能合。

![你来验收](/github/06.webp)

## 先把规矩写下来

AI 编程助手会读项目根目录的说明文件，不同工具认的文件名不同，常见的是 `AGENTS.md` 或 `CLAUDE.md`。把前五课的规矩写进去，它每次开工前都会照着做：

```markdown
## Git 和 GitHub

- 不直接改 main。一个 Issue 一条分支一个 PR，PR 说明写 Closes #编号。
- 推送前在本地跑 npm run build 和 npm test，通过了再推。
- 一个提交只做一件事，提交说明用 feat: / fix: / docs: 开头。
- 不强推，不用 git reset --hard，除非我明确同意。
- 不提交 .env、密钥、客户数据和大文件。
- CI 红了先读日志找第一条报错，修好再推，不要直接重跑。
```

写一次，所有任务都受它约束，不用每次在对话里重复。

## 你只看这四处

AI 说「做完了」不等于做完了。打开 PR 看：

1. **Files changed：** 改动是不是都和这个 Issue 有关。夹带了无关文件，或者删了不该删的东西，打回去。
2. **Checks：** 全绿。红的或者还在跑，都不算完。
3. **合并之后：** 部署那次运行成功了，Issue 自动关了。
4. **线上：** 打开真实地址，亲手点一遍改到的功能。

这四处都过了，才叫做完。

## 同时开好几个任务时

让 AI 同时做几件事，每件事要在自己的分支和目录里做，互不干扰。Git 提供的这种「一个仓库、多个工作目录」叫 worktree。

目录多了以后最容易出的错，是看目录名字猜它是哪条分支。确认的办法是在目录里跑：

```bash
git worktree list      # 每个目录对应哪条分支、哪个提交
git status             # 当前在哪条分支、有没有没提交的改动
```

名字里写着 `main` 的目录，里面不一定是最新的 main。真实事故见 [一次 worktree 认错主线，最后把系统打瘫的事故](/cases/worktree-baseline-incident)。概念细节见 [仓库、分支、PR 与 worktree](/guide/github-workflow)。

## 这一步谁来做

| 交给 AI 的 | 你要判断和验收的 |
|---|---|
| 按规矩开分支、提交、开 PR、修 CI、合并后的清理 | 规矩本身写得对不对；每个 PR 的四处检查；出事时让它先拿证据，不要先动手改 |

## 练习

把上面那段规矩放进你项目的 `AGENTS.md` 或 `CLAUDE.md`，开一个 Issue，让 AI 从头做到开 PR。你按四处检查验收，有一处不过就让它改，直到全部通过再合并。
