## 本章要回答

这个系统给谁用、是什么形态；餐厅怎么点单、出餐、收款，哪几步交给系统；系统要记住哪些东西、订单会经历哪些状态。

## 示例项目推进到哪

画出点单流程、角色和订单状态。

这一章读完，你能做三件事。第一，用几句话说清餐厅后台是什么形态、给谁用、这次不做什么。第二，画出餐厅从点单到出餐的流程，分清哪几步留给人、哪几步交给系统。第三，拿到 AI 设计的数据和订单状态以后，用业务话去检查它，找出它和真实餐厅对不上的地方。

你不需要会设计数据表。表交给 AI 设计。你要会的是另一件事：看着一张表或一条状态规则，问一句「这在店里对得上吗」。

AI 写代码很快。流程想错了，它会很快把错的流程写成代码。所以这一章放在写代码之前。

## 先说清它是什么形态、给谁用

「帮我做一个系统」不能直接拿去执行。用户从哪里进来、谁来操作、数据放在哪里、最后怎么上线，都还没有答案。

动手之前，先定产品形态。产品形态就是这个东西最后以什么样子交到用户手上。常见的有这几种：

| 形态 | 谁在用 | 验收时主要看什么 |
| --- | --- | --- |
| 官网、落地页 | 来访的潜在客户 | 手机和电脑上都正常显示，按钮和表单能用 |
| Web 应用 | 登录后的用户 | 关键流程走得通，数据存得对，不同角色看到不同功能 |
| 小程序 | 微信、支付宝等平台里的用户 | 真机上正常，登录、支付、分享可用，能过审核 |
| 移动 App | 高频使用的用户 | 主流机型上稳定，能发新版本，出问题能回退 |
| 管理后台 | 运营、客服、财务、店员 | 列表、搜索、编辑完整，危险操作有确认，关键操作有记录 |
| API 服务 | 别的系统 | 字段、错误码、权限规则写得清楚 |
| 脚本和内部工具 | 自己或团队 | 输入输出清楚，失败有提示，重复运行不坏数据 |

形态不同，交付方法就不同。小程序要过平台审核，App 要上应用商店，管理后台要管好权限和操作记录。每种形态的细节可以看站内的 [产品形态](/guide/product-forms)。

餐厅后台是管理后台。用它的是店员和店长，不是来吃饭的顾客。顾客不会打开它。

这个判断会直接影响后面的取舍。它不需要漂亮到能吸引顾客。它需要在午饭高峰被店员连着点几十次也不出错。它必须在浏览器里能用，做成手机 App 只是加分。

动手前，我会先把下面六项填完。这是餐厅后台的版本：

```text
产品形态：管理后台，在浏览器里使用
目标用户：店员（录单、接单、推进订单）、店长（维护菜单和价格、调整营业设置、看经营数据）
核心场景：高峰期录单、接单、出餐，不漏单，不算错钱
需要交付的端：Web 后台 + 后端接口 + 数据库
暂时不做：顾客自助点单、在线支付、外卖配送、会员积分
验收方式：用一组真实的点单场景从头走到尾，金额和订单状态都对
```

六项里有一项填不出来，就先别讨论用什么框架。框架选得再熟练，也只能证明代码能跑，证明不了东西能交付。

## 去看店里现在怎么转

需求文档一般只写「希望系统有什么功能」，很少写业务每天是怎么运转的。设计系统的第一步，是把现在的做法还原出来。

放到餐厅里，至少要问清这几件事：

| 要问的 | 在餐厅里具体问什么 |
| --- | --- |
| 谁参与 | 谁点单，谁记单，谁做菜，谁收钱，谁有权退菜 |
| 什么时候开始 | 顾客当面点，还是电话来单、外卖平台来单 |
| 依赖什么信息 | 菜单、今天哪些菜卖完了、价格、税率 |
| 按什么规则判断 | 什么情况下接单，什么情况下拒单 |
| 怎么交接 | 单子从前台到厨房怎么传，最容易在哪一步丢 |
| 出了意外怎么办 | 顾客改菜、菜卖完了、做好了没人来取 |
| 结束后留下什么 | 一单做完留什么记录，月底谁要看这些记录 |

问这些问题的时候，有一个坑：用户会配合你。

你问老板「要不要做一个顾客管理功能」，他多半说「有用」。说「有用」不花他任何成本。每天打开系统、把老客人一个个录进去、让店员改掉原来的习惯，成本完全不同。访谈里的好话，不能当成他真的会用的证据。

换一种问法。别问将来，问过去：

- 昨天中午最忙的时候，一张单从顾客开口到端上桌，经过了几个人？
- 上一次出错是什么时候？错在哪一步？后来怎么补救的？
- 现在用什么记单：纸条、收银机、还是微信群？
- 月底算账，你看哪几个数？这些数从哪里抄来的？
- 你记得住哪些常客？靠什么记？

过去的事里有代价，有当时的做法，有替代方案。将来的表态里只有想象。

一个需求值不值得做，看他现在为它付出了什么。如果老板已经在用脑子记常客、用纸条传单、每晚对着小票算账，这些笨办法就说明问题是真的。系统要替换的，就是这些笨办法。

我以前在餐馆打工。老板跟我讲要讲良心，蔬菜要放进肉汤里泡，才有味道。他记得每个常来吃的人，时不时给同学送菜、免单。生日当天来吃，可以免费。15 块钱四五个菜，他的餐口永远排队最长。

他没有任何系统。顾客档案全在他脑子里：谁常来，来过几次，爱吃什么，大概愿意花多少钱。

餐厅后台里有一个顾客页面，显示每个顾客的联系方式、下过几单、一共花了多少、最近一次什么时候来。这个页面要做的事，就是把老板脑子里那份档案存进系统，让店员换了人也能接上。

先看到老板在做什么，再决定系统做什么。顺序反过来，你做出来的就是你想象中的那家餐厅。

## 哪几步交给系统

流程画出来以后，下一步是分工。一个能落地的系统，会把工作分成三类：

| 工作类型 | 由谁来做 | 餐厅里的例子 |
| --- | --- | --- |
| 业务决策 | 负责全局的人，这里是店长 | 定价格，定税率，今天暂停营业，某道菜下架，特殊情况退单 |
| 业务执行 | 一线的人，这里是店员和厨房 | 录单，接单，开始做，出餐，交给顾客 |
| 确定性计算 | 系统自动完成 | 算小计、税和总价；检查菜能不能卖；检查是否在营业；统计今天的收入和热门菜 |

「确定性计算」指规则写得死、谁来算结果都一样的事。这类事交给系统，人就不用再算，也不会算错。

餐厅后台里有几个具体的例子：

- 金额由系统算。前端页面不能把价格传给后端，后端按菜品当前价格和税率自己算。这样店员手滑改不了价，有人绕过页面直接调接口也改不了。
- 「暂停营业」是店长的一个开关。开关关掉以后，系统直接拒收新单，店员不用一个个跟顾客解释。
- 「自动接单」也是店长的开关。打开以后，新订单进来时系统替店员按下「接单」。要不要开，是店长的决定；开了以后怎么执行，是系统的事。

系统提高效率，不等于给每个人更多按钮。它要做到这几件事：同一条信息不用在纸条、表格和系统之间抄来抄去；没有决定权的人改不了关键数据；能自动判断的步骤不用等人；所有人看的是同一份数据；出了问题能查到谁在什么时候改了什么。

还有一件事要说清：这一版餐厅后台记录金额，但不收钱。钱还是在收银台收。在线支付放到 [第 9 章](/book/ch09)。哪几步交给系统，也包括哪几步这次先不交。

想看这套分工方法在别的系统里怎么用，可以读站内的 [从业务流转到系统设计](/guide/system-design)，里面有一个排班系统的完整例子。

## 系统要记住哪些东西

流程和分工定了，系统要保存的数据就清楚了。餐厅后台要记住六样东西。我用业务话把它们列出来：

| 要记住的 | 用业务话说 | 要留意的地方 |
| --- | --- | --- |
| 菜单分类 | 主食、小菜、饮品，按什么顺序排 | 顺序由店长定 |
| 菜品 | 名字、介绍、图片、价格、现在能不能卖 | 「能不能卖」是一个开关 |
| 顾客 | 名字、电话、邮箱 | 电话和邮箱可以不填 |
| 订单 | 谁点的、走到哪一步了、小计、税、总价、备注、下单时间 | 走到哪一步只能按规则变 |
| 订单明细 | 这一单点了哪几道菜、各几份、当时的单价、这一行多少钱 | 菜名和单价按下单那一刻存一份 |
| 点单设置 | 备餐要多久、是否自动接单、是否营业、税率、营业时间 | 全店只有一份 |

这张表里有三个地方，最能看出设计有没有想到真实业务。你不用懂代码，用业务话就能检查。

第一，钱用「分」来存。12.50 元存成 1250。电脑算带小数的数会有很小的误差，钱不能有误差。检查方法：问 AI「金额字段是不是整数，单位是不是分」。

第二，订单明细里要抄一份下单时的菜名和单价。下个月菜涨价了，上个月的订单金额不能跟着变。菜改了名，旧订单上也应该是当时的名字。检查方法：改一道菜的价格，再打开一张旧订单，看金额变没变。

第三，下过单的菜不能随手删。删了，旧订单就找不到这道菜。卖完了、不做了，用「不可售」开关。我在餐厅后台里给删除加了保护：被订单用过的菜只能暂停，不能删除。检查方法：找一道有人点过的菜，试着删掉它，看系统拦不拦。

数据的定义只放在一个地方。餐厅后台里，数据表是唯一的源头，接口说明和前端用的类型都从它生成。我在陪玩系统里做报表字段时也守着同一条：字段字典只有一份主文档，数据库、接口、小程序和测试都以它为准，不在别处再抄一套规则。规则抄成两份，迟早会改了一份、忘了另一份。

## 订单会经历哪些状态

状态，就是一张订单此刻走到了哪一步。状态机是一张规定「从哪一步能走到哪一步」的表。

餐厅后台的订单有六个状态：

| 现在的状态 | 下一步可以变成 | 在店里对应什么 |
| --- | --- | --- |
| 待接单 | 已接单、已取消 | 新单进来，店员决定接还是不接 |
| 已接单 | 制作中、已取消 | 单子交给厨房 |
| 制作中 | 待取餐、已取消 | 厨房在做 |
| 待取餐 | 已完成、已取消 | 菜做好了，等人来取 |
| 已完成 | 不能再变 | 菜交到顾客手里，这单结束 |
| 已取消 | 不能再变 | 这单终止 |

开了自动接单的话，新订单直接从「已接单」开始。

这张表只有六行，但它决定了系统能不能被信任。

最常见的错误做法，是把状态当成一个普通字段：前端传什么，后端就存什么。这样做，店员点错一下，或者有人绕过页面直接调接口，就能把一张「待接单」改成「已完成」，这笔钱就算进了今天的收入。

餐厅后台的做法是：后端不接受「把状态改成某个值」，只接受动作，比如接单、开始做、出餐、完成、取消。每个动作进来，先查这张表。不在表里的跳转一律拒绝，并返回一个说得清原因的错误，比如「不能把订单从已完成改成已取消」。

拿到 AI 给的状态表以后，你要一行一行用业务话去问。下面是我问过的几个问题：

- **已完成的单还能取消吗？** 表里不能。那顾客吃完说菜有问题要退钱，怎么办？这是退款，不是取消，要单独设计。放到第 9 章讲。
- **菜做到一半，顾客走了，能取消吗？** 表里能。那已经做出来的菜算不算损耗？这一版不记。商用以后，店长可能要看这个数。
- **能不能从待接单直接跳到已完成？** 不能。可小店会嫌麻烦：「店里就我一个人，接单、做菜、出餐都是我。」这时可以做一个按钮，一次推进好几步，但每一步仍然按表走，记录一条都不少。
- **谁有权取消？** 这一版没有登录，谁打开后台都能取消。商用时要分角色，取消要留下是谁、什么时候、为什么。放到 [第 10 章](/book/ch10) 讲。

状态是从业务里长出来的，不能从别的项目抄。陪玩系统的订单状态是待支付、待交付、交付中、已完成、已取消。它先收钱，再提供服务，所以第一个状态是「待支付」。餐厅后台这一版不收钱，第一个状态就是「待接单」。两个系统都叫「订单」，状态完全不同。陪玩系统那几个状态，我是列成表格交给甲方逐行确认的。第 4 章会讲这份确认清单怎么写。

## 有页面，不等于流程通了

AI 很会把页面填满。页面上有按钮、有列表、有数字，看起来很完整。可页面存在，不代表业务走得通。

陪玩系统有五个端：顾客、陪玩、接待、管理员，还有超级管理员。有一次，我对着需求文档把五个端逐个审了一遍。审查的口径很严：只有真实接口、数据真的存下来了、权限有检查、出错有处理、能验证，五样都成立，才算对上了需求。

审下来，每个端都只是「部分对齐」。差距主要不在缺页面，而在页面背后的流程没闭环。还查出几处更麻烦的偏差：

- 超级管理员首页把普通订单当成「待审批」展示，把已经付过钱的流水当成「高风险提现」展示。页面看起来很忙，可展示的东西和业务含义对不上。
- 高风险复核页面上放着编出来的占位记录。没有真实数据时，它显示假数据。它应该显示「暂无记录」。
- 管理端有一个留言页，代码写好了，但没注册进小程序，用户根本打不开。

这几处偏差有一个共同点：代码能跑，页面能看，业务含义是错的。它们会让用的人做出错误的判断。所以我把它们排在最前面修。

检查方法很朴素：页面上的每一条数据，问三个问题。它从哪来？谁来处理它？处理完以后去哪？三个问题答不上来的，就是还没打通的地方。

## 交给 AI 的

这一步交给 AI 的，是根据你讲清的流程设计数据和状态，再写成代码。关键是先设计、后写代码，中间你要确认一次。

可以直接复制下面这段，把方括号里的内容换成你自己的项目：

```text
这是一个餐厅运营后台，形态是管理后台，在浏览器里使用。
使用者：店员（录单、接单、推进订单）、店长（维护菜单和价格、调整营业设置、看经营数据）。

业务流程：
1. 店员为顾客录入订单：选择顾客、菜品和数量，可以填备注。
2. 系统检查是否在营业、顾客是否存在、每道菜是否可售。任何一项不满足，拒绝下单并说明原因。
3. 金额由服务端按菜品当前价格和税率计算，不接受前端传来的任何价格字段。金额用整数分保存。
4. 订单状态：待接单 → 已接单 → 制作中 → 待取餐 → 已完成。前四个状态都可以取消。已完成和已取消不能再变。开启自动接单时，新订单直接进入已接单。
5. 订单明细保存下单时的菜名和单价，菜品改价、改名不影响旧订单。
6. 被订单用过的菜品不能删除，只能设为不可售。

请先不要写代码。先输出三样东西：
- 你打算保存哪些数据，每样数据有哪些字段，每个字段用一句业务话解释；
- 订单状态转换表，以及每个转换由什么动作触发；
- 这个流程里你认为还没说清楚的地方，列成问题问我。
我确认以后，你再写代码。
```

你确认设计以后，再发第二段：

```text
按刚才确认的设计实现。要求：
- 状态转换规则只写在一个地方，所有改状态的接口都调用它；
- 后端只接受动作（接单、开始制作、出餐、完成、取消），不接受直接改状态字段；
- 非法的状态跳转返回明确的错误，说明从什么状态不能变成什么状态；
- 为每一条非法跳转写一个测试。
```

AI 列出来的「没说清楚的地方」要认真看。它问的问题，往往就是你没去店里问的问题。答不上来，就回去问老板。

## 你要判断和验收的

你不用读懂每一行代码。下面这些检查，用业务话就能做：

**形态和范围**

- [ ] 能用一句话说清：这个系统给谁用，在哪里用，这次不做什么。
- [ ] 「暂时不做」写下来了，而且对方知道。

**流程和分工**

- [ ] 流程来自真实观察。至少问过一次「上一次……的时候是怎么做的」。只问过「你需要……吗」，不算。
- [ ] 每一步都有负责人。哪一步是店长拍板，哪一步是店员执行，哪一步由系统计算，分得清。
- [ ] 能说出系统替换掉了哪个笨办法。

**数据**

- [ ] AI 列出的每样数据，你能说出店里谁会用到它。说不出来的，问它为什么要有。
- [ ] 金额用整数分保存，由服务端计算。
- [ ] 改一道菜的价格，旧订单的金额不变。
- [ ] 删除一道被点过的菜，系统拦住了。

**状态**

- [ ] 拿着状态表，一行一行问「店里会不会这样」。
- [ ] 亲手试三次非法跳转：待接单直接改成已完成、已完成改成已取消、已取消改成已接单。三次都被拒绝，提示说得清原因。
- [ ] 打开自动接单，新建一单，确认它直接是「已接单」。

**异常场景**

- [ ] 暂停营业时下单，被拒绝。
- [ ] 点一道已设为不可售的菜，被拒绝。
- [ ] 连续快速点两次「提交」，看会不会生成两张一样的单。

**页面**

- [ ] 页面上没有编出来的占位数据。没有数据时，显示的是空状态。
- [ ] 页面上每一条数据都答得出：从哪来，谁处理，处理完去哪。

这些检查做完，你手上就有了一张经过业务确认的流程图、一张数据清单和一张状态表。下一章用它们去挑技术方案。

## 这一步谁来做

| 交给 AI 的 | 你要判断和验收的 |
|---|---|
| 让 AI 根据你讲清的流程设计数据和状态，写成代码。 | 流程和角色是不是真实业务；订单状态能不能乱跳。不用会设计数据表，但要会用业务话检查它。 |
