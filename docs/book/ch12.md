# 第 12 章　报价、排期与需求变更

## 本章要回答

「多少钱、多久交」怎么回答；哪些钱不该接；需求变了怎么重新估。

## 示例项目推进到哪

给 餐厅后台写一份报价单，处理一次需求变更。

## 先说结论

读完这一章，你能做三件事：

- 客户问「多少钱、多久交」时，拿出一份写清范围的报价单，而不是只报一个数字。
- 判断一笔钱该不该接。
- 需求中途变了，按固定步骤重新估时间和价格，并让对方书面认账。

这一章只有一条验收标准：报价、范围和每一次变更，都有书面记录，双方都认过。聊天记录里对方回一句「可以」也算书面，前提是你能找到它，并且能对上是哪个版本。

## 一句「OK」埋下的雷

序里讲过我的第一单。2024 年暑假，一个不到 2000 元的项目，老板问我什么时候能做完，我很快回了一句「OK」。

需求没问清，演示方式没确认，修改范围没约定，部署、交付和后续维护也都没说。我怕问多了对方觉得我不会，怕时间说长了对方换人，怕把风险讲在前面显得自己能力不够。于是先答应，先开工。

开工以后，没问出口的问题一个接一个回来。演示完一版，又有新的修改。对方很难一次说清自己想要什么，我只能做出来，再让他判断对不对。钱已经谈好了，责任却没有边界。每冒出一个问题，我唯一会做的就是继续加时间。有一晚我几乎没睡。

回头看，那次的问题不在技术。新手接单遇到的第一个对手，往往是自己想赶紧答应的冲动。你以为在抓机会，其实是把所有没说清的风险，提前接到了自己身上。

AI 编程让这件事更危险。AI 能把三天的开发压到几个小时。如果需求没问清，几个小时以后你只是更早拿到一个方向错误的版本。写得越快，错误越早变成实物。

## 报价是给整条责任链定价

AI 写得快以后，新手最常见的心理是不敢收钱：这个功能 AI 十分钟就生成了，我报 2000 会不会太贵？

这个想法会把人推向一个危险动作：先报低价，把订单拿下来再说。订单可能拿到了，需求确认、部署、测试、沟通、修改和售后，并不会跟着降价。

客户买的是一个能用的结果。为了交出这个结果，你要做的事远不止写代码。拿餐厅后台举例，把一次交付拆开看：

| 工作 | 内容 | AI 能帮多少 |
|---|---|---|
| 问清需求 | 谁用，点单到收款怎么走，哪些这次不做 | 几乎帮不上 |
| 拆任务 | 菜单、订单、顾客、设置、经营首页拆成能验收的小任务 | 能列初稿 |
| 写代码 | 页面、接口、数据表 | 帮得最多 |
| 测试 | 下单金额、状态流转、越权 | 能写测试，测得对不对要你判断 |
| 部署上线 | 域名、环境变量、自动发布 | 能配，线上能不能打开要你验证 |
| 沟通和修改 | 演示、收集反馈、改 | 帮得很少 |
| 交付和售后 | 说明文档、账号移交、上线后出问题 | 能写文档，责任在你 |

AI 节省的是你的执行时间。这部分时间来自你的工具、经验和判断，不需要主动折价送给客户。报价要覆盖整张表，不只是第三行。

## 报价单写什么

报一个数字很容易，难的是让这个数字有边界。我现在每次报价，至少写清五件事：

1. 做哪些功能；
2. 不做哪些功能；
3. 交付什么文件或链接；
4. 周期多长；
5. 包含几次修改，什么时候付定金和尾款。

少了第 2 条，对方会默认「我想到的都包括」。少了第 5 条，修改会变成无限次。

一个 500 元的单子，边界清楚，也能成为一次完整的训练。一个 3000 元的单子，边界不清，也可能把你拖到怀疑人生。第一单不一定要大，但它一定要能结束。

下面是给餐厅后台写的报价单骨架。假设客户是一家单店餐厅的老板，想要一个给店员用的运营后台。金额按你自己的单价填。

```text
项目：XX 餐厅运营后台（第一期）

一、本期包含
1. 菜单：分类、菜品、价格、可售/停售
2. 订单：店员代客下单，订单列表与筛选，按固定流程推进状态
   （待接单 → 已接单 → 制作中 → 待取餐 → 已完成；完成前任一步可取消）
3. 顾客：联系方式、消费金额、下单次数
4. 设置：备餐时间、自动接单、营业状态、税率、营业时间
5. 经营首页：当日收入、订单量、待处理订单、热门菜品
6. 店长、店员两个角色；店员不能改价格和设置

二、本期不包含（需要时另行报价）
- 顾客自助点单小程序、在线支付、外卖平台对接
- 会员积分、优惠券、多门店
- 打印小票、对接收银机

三、交付物
- 线上访问地址和店长账号
- 源代码仓库（移交到甲方账号下）
- 运行说明、部署说明、运维手册各一份
- 验收清单一份

四、周期
- 开工后 X 个工作日交付第一版
- 甲方在收到第一版后 X 个工作日内反馈，逾期顺延

五、修改与付款
- 验收期内，本期范围内的问题免费修改
- 本期范围外的改动，按变更流程另行确认
- 签约付定金 X%，验收通过后付尾款
- 上线后的维护另签维护约定

甲方确认：　　　　　日期：
```

这份骨架里最值钱的是第二部分「本期不包含」。它把对方脑子里那些没说出口的期待提前摆到桌面上。老板看到「在线支付不包含」，要么接受，要么当场提出来，你当场报价。两种结果都比做完以后再吵好。

订单状态那一行也值得写进报价单。状态流程是业务规则。写清楚以后，「为什么不能从待接单直接跳到已完成」就是双方确认过的规则，不会在验收时被当成你的 bug。第 2 章讲过怎么跟老板确认这些状态。

## 时间怎么估

「多久交」比「多少钱」更容易答错，因为新手只估写代码的时间。

我估时间分三步。

第一步，先拆任务。按[第 4 章](/book/ch04)的方法，把需求拆成一个个能验收的小任务，每个任务写清做完是什么样子。拆不下去的地方，就是需求还没问清的地方。先回去问，不要估。

第二步，每个任务估两个时间：AI 写出来要多久，你验收、修改到能交要多久。后一个通常比前一个长。AI 十分钟写完一个页面，你确认它在手机上不乱、数据对、权限没漏，可能要一个小时。

第三步，加上不写代码的时间：等对方回复、演示、改反馈、部署、写文档。这部分不全在你手里。客户可能三天才回一次消息，审查可能卡在某个负责人那里。[第 14 章](/book/ch14)会讲到，我用 AI 七天能把项目做到能运行，甲方从审查到正式用起来还要一个月以上。这部分时间要单独写进排期，并写明「甲方 X 个工作日内反馈，逾期顺延」。不写，延期就全算在你头上。

排期按里程碑写，不只写一个总日期：

| 里程碑 | 交付什么 | 谁来确认 |
|---|---|---|
| 需求确认 | 报价单和范围，双方签字 | 老板 |
| 第一版 | 线上地址，能走通下单到完成 | 老板试用 |
| 修改完成 | 按反馈修改后的版本 | 老板 |
| 验收 | 按验收清单逐条过 | 老板签字 |

每个里程碑都有一个看得见的东西。对方随时知道进度，你也随时知道事情卡在谁那里。

## 哪些钱不该接

能不能接，比报多少更重要。

我早期什么单都接：期末作业、毕设、商单、长期单，后来还接手过独立维护几十万行代码的系统。钱越来越多，项目越来越复杂，看起来一直在往上走。后来我才发现，这些活虽然长得不一样，底层买的常常是同一种东西：我的待命、手速、忍耐和快速响应。

有一晚快一点，我把最后一版代码发出去，对方回「老师靠谱，款我打了」。收款通知弹出来，我的第一反应却是去看明天还有几个消息没回、几个需求没补。钱到账了，人没有被托起来。

现金流本身没有错。没有稳定现金流，人会慌，人一慌，判断就会变形。原本不想接的活会接，原本不想忍的人会忍。问题出在低水平的现金流上：它让你今天活下来，同时切碎你的时间，让你越做越便宜。

现在如果有 1500 元以下的单子找我，我大概率会婉拒。这点钱当然也是钱，但低预算后面通常跟着别的东西：边界低、需求清晰度低、对方的预期管理能力低。你接的是一个小活，后面往往跟回来一堆返工、解释和上下文切换。它吞掉的是你那天晚上最整块的脑力。

我现在判断一笔钱值不值得长期做，看四件事：

1. **它是不是高度依赖我本人一直在线。** 我回消息慢了对方就不满意，这笔钱租的是我的待命状态。
2. **它是不是做得越多，越容易被替代。** 投入越多只是越熟练，并没有变得更稀缺。
3. **它是不是在持续破坏我的时间结构。** 回款建立在频繁切换、处理低价紧急琐事、把最好的时间拿去补洞上。
4. **它有没有累积。** 做完以后，能不能留下作品、案例、方法、口碑或议价权。

前三条里占了两条，这笔钱大概率是坑。

AI 让这个判断更重要。一笔钱如果只买你的手速和通用动作，它一定会越来越便宜，因为工具也能做，别人也能做。还能撑住价格的是更靠后的东西：对业务的理解、对结果的判断、在复杂环境里交付的能力、出了问题能不能扛住责任。

对刚起步的读者，我不建议一开始就挑三拣四。第一单的目的是走完一条完整链路。从第二单开始，再用这四条筛一筛。

## 需求变了怎么办

需求一定会变。这不全是客户的错，很多人看到东西之前，确实说不清自己要什么。

陪玩系统是一个例子。从 4 月 13 日到 5 月 13 日这一个月，它从「基础页面能用」补到了顾客、陪玩、接待、管理、超级管理员五类角色都能跑通核心业务。那个月的修改总结写了十几页：顾客端补订单和消费记录，陪玩端补入驻审核和提现，接待端补代客建单和异常处理，后台补资金、角色和系统配置，权限也收紧了一轮。其中不少需求是开工时没想到、做着做着才冒出来的。

同一份总结里还有一条：「移除未使用或暂不交付的后台模块」。变更不只是加，也有减。减掉的东西同样要记下来，否则验收时对方会问「那个页面去哪了」。

变更本身不可怕，可怕的是变更没有记录。客户说「顺手加个功能」，你说「好的」。这样来三次，范围已经变了一倍，价格和工期没动，也没人记得是从哪一次开始变的。

我处理变更用五步：

1. **先记下来。** 原话记下来，标日期、编号，不管多小。
2. **说清改什么、不改什么。** 把一句话的要求翻成具体的变化。
3. **估影响。** 影响哪些已有功能，数据要不要改，要补哪些测试，要多几天，要加多少钱。
4. **书面确认。** 把影响发给对方，对方回复同意，再开工。
5. **更新范围。** 把这条变更并进报价单的范围和验收清单。

拿餐厅后台走一遍。第一版交付前一周，老板说：「顾客来多了，加个会员积分吧，消费一块钱积一分。」

一句话，听起来是一个小功能。按第 3 步拆开：

| 影响到哪 | 具体要定什么、做什么 |
|---|---|
| 数据 | 顾客多一个积分余额，还要有积分流水，记清每一笔怎么来的 |
| 订单 | 订单完成时加积分；订单取消时，已加的积分要不要扣回 |
| 金额 | 按税前还是税后算，不足一元怎么处理 |
| 使用 | 积分能不能抵钱；抵钱以后，经营首页的收入怎么算 |
| 权限 | 谁能手动调整积分，调整要不要留记录 |
| 测试 | 下单加分、取消扣分、手动调整，三种情况都要有测试 |
| 时间和费用 | 第一版延后几天，加多少钱 |

列完这张表，老板通常会自己缩范围：「先只积分，不抵钱；取消就扣回；只有店长能调。」范围缩了，你估的时间也有了依据。第 2 步和第 3 步的价值就在这里：把一句话翻成具体动作，让双方都看见代价。

变更单可以很短：

```text
变更编号：03
提出人 / 日期：老板 / 某月某日
原话：加个会员积分，消费一块钱积一分
确认后的范围：
  - 订单完成时按实付金额（含税，不足一元的部分不计）加积分
  - 订单取消时扣回已加积分
  - 只有店长能手动调整积分，每次调整留操作记录
本次不做：积分抵扣、积分商城、会员等级
影响：第一版交付延后 X 个工作日；费用增加 X 元
新增验收项：下单加分、取消扣分、店员无权调整积分
甲方确认：
```

小改动要不要也走这一套？我的标准是：改一行文案、换一个颜色，记一笔就做；凡是动到数据、金额、权限、状态的，五步走完。[第 6 章](/book/ch06)讲过，钱、数据、权限不能乱，变更也一样。

## 这一步交给 AI 做什么

这一章的事主要靠你自己去谈，但有三件事 AI 能帮上忙。

第一，拆任务、估工作量。把你和客户确认过的需求贴给 AI：

```text
下面是客户确认过的需求。请把它拆成可以单独验收的任务，每个任务写：
1. 做完以后用户能看到什么、能做什么；
2. 怎么验收（用一句话描述一个真实操作）；
3. 依赖哪些前置任务；
4. 实现大概要多久、我验收和修改大概要多久，分开写。
最后单独列出：需求里没说清、需要我回去问客户的问题。
不要写代码。
```

最后那一条最有用。AI 列出的「没说清的问题」，就是你下一次和客户沟通的提纲。

第二，变更影响分析。客户提出变更以后，在项目仓库里让 AI 读代码：

```text
客户提出一个变更：「消费一块钱积一分」。
请先读当前项目的数据表、下单服务、订单状态流转和相关测试，然后列出：
1. 要改哪些文件、哪些数据表；
2. 会影响哪些已有功能；
3. 需要新增或修改哪些测试；
4. 有哪些业务规则需要客户拍板（例如订单取消时积分怎么处理）。
只做分析，不改代码。
```

第三，整理文书。把你和客户聊定的要点给 AI，让它按上面的骨架整理成报价单或变更单，你再逐条核对。

AI 给的时间估计只能当参考。它不知道客户回消息有多慢，也不知道你明天还有别的事。最终的数字你来定。

## 你要判断和验收的

每次报价和变更前，对照这张表：

- [ ] 报价单写了「本期不包含」，并且对方看过。
- [ ] 交付物逐项列出：线上地址、账号、代码仓库、文档。
- [ ] 周期按里程碑写，甲方反馈需要的时间单独写出，并写明逾期顺延。
- [ ] 修改次数或修改范围写清，范围外的改动走变更。
- [ ] 定金、尾款和付款时间写清。
- [ ] 订单状态、金额算法这类业务规则写进了范围，双方确认过。
- [ ] 这一单用四条标准筛过：不靠我一直在线、做多了不会更便宜、不切碎时间、能留下案例。
- [ ] 每次变更都有编号、原话、确认后的范围、影响和对方的确认。
- [ ] 变更确认后，报价单的范围和验收清单已经同步更新。
- [ ] 所有确认都能找到原文。聊天截图或邮件都可以，但要存档。

最后一条看起来最琐碎，到验收和收尾款的时候最管用。
