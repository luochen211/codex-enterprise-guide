读完这一章，你能列出一个能演示的项目离能收钱还差哪些东西，并分清哪些这次必须补、哪些可以以后再说。你还会拿到一段提示词，让 AI 对照清单检查你的项目缺了什么。

## 七天做完，一个月才用上

现在用 AI 编程，七天已经足够我把一个项目做到能运行、能交付的状态。需求拆出来，功能做出来，问题修完，项目也能跑起来。从开发者的角度看，这件事已经落地了。

同样的项目进入一家成熟企业，从交付到业务部门用上，通常还要一个月以上。

代码完成以后，甲方还要审查。业务流程要确认，权限和数据要检查，相关负责人要判断能不能接进现有系统，最终使用的部门也要验收。不同企业审查的项目各不相同，但等待、确认和修改，几乎不会随着代码写完一起消失。

开发者用自己的任务判断进度：代码写完了，页面能打开，核心功能能运行，部署也完成了，就觉得项目接近终点。企业看的是另一条链路：这套系统是否符合原来的业务规则，数据会流向哪里，谁有操作权限，出了问题怎么处理，最终由谁批准上线。能运行，只是企业愿意用它的第一个条件。

可以算一笔账。假设一个项目原来要三十天，其中七天开发，其余时间在等待、审查和验收。AI 就算把开发再压到三天，整个项目也只缩短了四天。你一天能交出三个版本，甲方一周只审得完一个。多出来的两个版本不会自动变成业务成果，它们会停在流程里排队。

管理学里有一个说法叫约束理论，由高德拉特提出：一条交付链在某个阶段，总有一个主要的卡点决定整体速度。马斯克讲过 Model 3 的「产能地狱」：一辆车大约有一万个独特部件，任何一个出问题，都可能拖慢整条生产线，生产线只能跟着最慢的那个部件前进。

开发能力不足时，写代码就是卡点。AI 把开发变快以后，卡点会往后移：移到需求确认，移到甲方审查，移到安全检查，或者移到某个有最终决定权的人身上。

审查也不一定是浪费。一个人做的小项目，发现问题马上就能改。企业系统一旦进入生产环境，影响的是客户数据、订单、资金、员工权限和品牌信用。开发者一句「我这里已经跑通」，替代不了业务负责人、安全人员和使用者的判断。

这对你有两个直接的影响。

第一，排期要按「对方用上」来算，不能按「代码写完」来算。报价和排期时，把对方审查和验收的时间算进去。这部分在[第 12 章](/book/ch12)细讲。

第二，你能帮对方缩短的，是审查的时间。审查慢，常常因为材料要反复补交，审查的人拿不到能直接判断的信息。测试证据、变更说明、风险清单、验收文档，这些材料 AI 都能帮你整理。你交得越齐，对方等得越少。

## 水面下的部分

本章的配图是一座冰山。水面上是页面和功能，演示时能看到。水面下是审查的人、使用的人和付钱的人要检查的东西。

拿我交付过的陪玩平台举例。它的说明文档第一页，就把交付基线写清楚了。

它有五个端：顾客端用来浏览陪玩师、下单、评价；陪玩师端用来接单、排班、看收益；接待端给客服和前台代客户下单、跟进订单；管理员端是小程序，负责日常运营；超级管理员端是网页后台，负责账号、角色权限、资金审核、日志审计和系统配置。

除了这些页面，交付基线里还写着：

- 生产环境部署和支付接入；
- 权限治理：普通管理员和超级管理员能做的事分开；
- 日志审计：关键操作留记录；
- 一个反向代理作为统一入口，负责 HTTPS 加密、域名和请求转发；
- 本地开发、测试、预发布、生产四套环境，各用各的配置；
- 部署时要支持数据库迁移、健康检查、日志收集、错误监控、配置校验和回滚。

这里有几个词先用一句话解释。数据库迁移，是改数据表结构时，按记录好的步骤一步步改，不把旧数据弄丢。健康检查，是系统留一个地址，定时访问它就知道服务还活着。回滚，是新版本出问题时，退回上一个能用的版本。

这些东西，没有一项能在演示时被看到。可少了任何一项，这套系统都不能交给一个每天有真实订单和真实资金的团队。

把它们归一下类，就是一个项目从 Demo 走到商用，水面下通常要补的部分：

| 类别 | 要回答的问题 | Demo 里常见的状态 | 本书在哪章讲 |
|---|---|---|---|
| 业务规则 | 订单有哪些状态、谁能推进到下一步 | 只做了正常路径 | 第 2 章 |
| 输入和错误 | 错误的数据会不会被拒绝，出错时用户看到什么 | 只在前端校验，后端照单全收 | 第 6 章 |
| 部署与环境 | 线上和本地是否分开，密钥放在哪，能不能回滚 | 只在自己电脑上跑 | 第 7 章 |
| 监控与日志 | 出了错谁先知道，能不能查到原因 | 错误只打印在终端里 | 第 8 章 |
| 备份与恢复 | 数据丢了能恢复到哪一刻 | 没有备份 | 第 8 章 |
| 钱 | 金额谁来算，支付成功怎么确认，退款和对账怎么做 | 价格从前端传给后端 | 第 9 章 |
| 账号与权限 | 谁能登录，每个角色能看什么、改什么 | 没有登录，或人人都是管理员 | 第 10 章 |
| 操作审计 | 关键操作有没有记录谁做的 | 没有 | 第 10 章 |
| 隐私与合规 | 收集了哪些个人信息，告知用户了吗 | 没想过 | 第 10 章 |
| 成本 | 每月花多少钱，用户多了以后花多少 | 没算过 | 第 11 章 |
| 交付与维护 | 使用说明、验收标准、出了事谁响应 | 代码发过去就算结束 | 第 14 章 |

## 为什么水面下的部分越来越值钱

这几年软件行业有两个变化同时发生。

一是做软件的门槛被 AI 打低了。内部工具、报表面板、小型后台、轻量的客户管理系统、自动同步脚本，过去要排期、要预算、要协调开发资源。现在一个懂业务的人，加上一套 AI 编程工具，很快就能交付出能运行的版本。能做出来的东西多了，就不稀缺了，价格也守不住。

二是压力更小的那类软件，都贴着真实业务和责任运行。支付、履约、物流、医疗、金融这些领域的系统，里面有长期的数据治理、复杂的权限、线下的协同流程，还有稳定性、审计和合规的要求。这些很难被一句提示词替换掉。

落到个人身上：如果你只会做水面上的部分，你和一个会用 AI 的业务人员差别不大。你能把水面下的部分也做好，客户才有理由付钱给你，并且长期用你。

## 餐厅后台：已经有的和还缺的

全书的例子餐厅后台，交上去的面试版本已经有这些：

| 方面 | 已经有的 |
|---|---|
| 功能 | 经营首页、订单、顾客、菜单、设置五个页面，都能实际操作 |
| 业务规则 | 后端校验必填字段，拒绝已下架的菜，订单金额由服务端计算，订单状态只能按规定的顺序变化 |
| 前后端约定 | 数据格式从数据表定义开始，一路自动生成到前端，前后端不各写一份 |
| 测试 | 后端测了下单和状态流转；前端测了部分关键逻辑 |
| 自动检查和发布 | 每次提交自动跑类型检查、测试、代码规范检查和构建；合并到主分支后自动发布前端 |
| 部署 | 前端、接口、数据库都在托管平台上，接口有健康检查地址 |
| 演示数据 | 一条命令灌入菜单、顾客、设置和 30 笔订单 |
| 文档 | README 写了怎么运行、怎么灌数据、怎么部署、架构为什么这样定、哪些地方做了取舍 |

按第 0 章的四个层次，它在「完整」这一层，而且做得比较扎实。但要交给一家真实的餐厅用、还要收钱，它还缺这些：

| 缺口 | 现在的状态 | 不补会怎样 |
|---|---|---|
| 登录和角色 | 没有登录 | 拿到地址的人都能改菜单、改价格、看顾客联系方式 |
| 在线支付 | 订单只记录金额 | 收不了钱，或只能靠人工对账 |
| 演示数据命令 | 运行时会先清空业务数据表 | 在生产环境误跑一次，真实订单全部消失 |
| 备份与恢复 | 没有自己的备份方案，也没演练过恢复 | 数据出问题时，不知道能恢复到哪一刻 |
| 监控和报警 | 只有一个健康检查地址，没人定时看 | 系统挂了，要等店员打电话来才知道 |
| 操作审计 | 没有操作记录 | 价格被改错了，查不到是谁、什么时候改的 |
| 隐私 | 存了顾客的联系方式，没有隐私说明 | 有合规风险，顾客投诉时说不清 |
| 成本 | 没算过 | 报价时不知道每月的运维费该收多少 |
| 交付与维护 | README 写给面试官看 | 店长不知道怎么用，出了事不知道找谁 |

这两张表放在一起看，就是本书后面十几章要做的事。

## 哪些现在补，哪些以后再说

缺口不用一次补完。全补完再上线，等于把第 0 章说的「让产品进入现实」又往后推了。

我用四个问题给每个缺口分级：

1. 出事时损失的是什么：钱、数据、个人信息、信任，还是只是体验差一点？
2. 出事的可能性有多大，现在有没有迹象？
3. 出事以后，能不能及时发现、能不能补救？
4. 补它要花多少，以后再补会不会贵很多？比如数据结构和支付方式，上线以后再改，代价比现在大得多。

按这四个问题，缺口大致分成三栏：

| 分级 | 标准 | 餐厅后台里的例子 |
|---|---|---|
| 这次必须补 | 出事会直接伤到钱、数据或个人信息，或者以后再补会很贵 | 登录和角色；禁止在生产环境运行清空数据的命令；备份 |
| 上线前补 | 决定了出事以后能不能知道、能不能恢复 | 监控报警；错误日志；回滚流程 |
| 以后再说 | 只有规模变大或业务变化才会出现 | 高并发优化；多门店；复杂报表 |

分级还要看客户要什么。假设第一家客户是一家小餐厅，只想让店员在店里用这套后台记订单，顾客不在线上下单。那么在线支付可以先放进「以后再说」，登录、备份和禁用清库命令仍然是必须的。如果客户想让顾客自己扫码下单、在线付钱，支付、对账和隐私说明就要挪进「这次必须补」。

同一份缺口清单，客户不同，分级就不同。所以分级要和客户一起确认，不能自己拍板。

## 交给 AI 的：对照清单查缺口

逐个文件去翻缺了什么，很费时间。这件事适合交给 AI。把下面这段发给你的 AI 编程助手，让它在项目仓库里运行：

```text
请先完整阅读这个仓库：README、目录结构、数据表定义、后端接口、测试、部署和 CI 配置、环境变量示例文件。

然后按下面的清单，逐项检查这个项目离商用还缺什么：
业务规则、输入校验和错误处理、部署与环境、监控与日志、备份与恢复、金额与支付、账号与权限、操作审计、隐私与个人信息、运行成本、交付文档与维护。

输出一张表，每行包含：
- 检查项
- 现状：已有 / 部分有 / 没有
- 证据：对应的文件路径、配置项或命令；找不到就写「未找到」
- 风险：不补的话，最坏会出什么事
- 补齐的工作量：小 / 中 / 大

要求：
1. 只根据仓库里能看到的内容判断。没有证据的写「未找到」，不要写「可能已有」。
2. 不要修改任何文件，不要安装依赖，不要运行会改动数据库的命令。
3. 表格后面单独列出：会直接造成资金损失、数据丢失或个人信息泄露的缺口。
4. 再列出仓库里有没有会清空或覆盖数据的脚本，写明它们在什么条件下会运行。
```

第 4 条是我加的。餐厅后台的演示数据命令会先清空数据表，这类脚本在演示阶段很方便，到了生产环境就是隐患。AI 读代码时容易把它当成普通工具略过去，所以要专门问一句。

## 你要判断和验收的

AI 的表格出来以后，你要自己做三件事。

**抽查证据。** 挑三到五条标成「已有」的项，自己打开对应的文件，或者跑一下对应的命令，确认 AI 没有看错。AI 常见的错误是：看到一个空的配置文件，就判成「已有」；看到一个函数名叫 backup，就以为备份在定时运行。

**分级。** 用上一节的四个问题，把每个缺口放进三栏：这次必须补、上线前补、以后再说。

**和使用方对齐。** 分级结果要给客户看，由客户确认。「以后再说」的部分，要写进交付说明的「已知限制」里，让对方知道它不在这次的范围内。

完成以后，用这几条检查：

- [ ] 缺口表每一行都有证据，或者明确写了「未找到」
- [ ] 你亲自抽查过至少三条「已有」
- [ ] 涉及钱、数据、个人信息的缺口，都在「这次必须补」或者有明确的理由说明为什么不补
- [ ] 每个「以后再说」都写了触发条件，比如「开第二家店时」「日订单超过某个数时」
- [ ] 能清空或覆盖数据的脚本，都确认了不会在生产环境运行
- [ ] 分级结果已经发给客户，客户确认过
- [ ] 排期里留出了客户审查和验收的时间

下一章从缺口表的第一行「业务规则」开始：先弄清这家餐厅的业务是怎么转的，再决定系统怎么做。如果想提前了解，可以先看[从业务流转到系统设计](/guide/system-design)。
