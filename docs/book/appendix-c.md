# 附录C　术语表

## 本章要回答

只收书里出现、读者需要能听懂的词，一句话解释。

按首字母排序。英文词按字母，中文词按拼音；同一个字母下，英文词在前。括号里是书中主要讲到它的章节。

## 数字

| 术语 | 解释 |
|---|---|
| 502 Bad Gateway | 一种报错：请求到了服务器门口的反向代理，代理找不到后面的应用，或者应用没回应。（第 13 章） |

## A

| 术语 | 解释 |
|---|---|
| Agent（智能体） | 能自己调用工具、分好几步完成一件事的 AI 程序，不只是一问一答。（第 1 章） |
| AGENTS.md | 放在仓库里给 AI 编程助手看的规则文件，写项目约定、禁止事项和验证命令。（第 5 章） |
| API（接口） | 程序之间约好的请求方式。前端通过接口找后端要数据、提交操作。（第 2、3 章） |

## B

| 术语 | 解释 |
|---|---|
| Basic Auth | 浏览器自带的一种简单登录保护，打开页面先弹窗要账号密码。常用来给管理后台多加一道门。（第 10、14 章） |
| bug | 程序里的错误，让系统没有按预期工作。 |
| 报价单 | 写清做什么、不做什么、交付物、周期、修改次数和付款节点的文件，双方确认后作为范围依据。（第 12 章） |
| 备案 | 在中国大陆用服务器对外提供网站或小程序服务前，要向主管部门登记的手续。（第 10 章） |
| 备份 | 把数据定期另存一份到别的地方。只有真的恢复过，才知道备份能不能用。（第 8 章） |
| 本机地址（127.0.0.1） | 代表「这台机器自己」的地址。只绑在这个地址上的程序，别的机器访问不到。（第 13 章） |
| 并发 | 多个请求在同一时间到达，比如两个人同时抢最后一份菜。处理不好会出现超卖、重复扣款。（第 8 章） |
| 部署 | 把代码放到服务器上运行，让别人能通过网址访问。（第 7 章） |

## C

| 术语 | 解释 |
|---|---|
| CI/CD（持续集成 / 持续部署） | 代码一提交就自动跑检查（CI），检查通过后自动发布到线上（CD）。（第 7 章） |
| 测试（自动化测试） | 用代码检查代码：给定输入，看输出是不是预期的结果。改完代码跑一遍，就知道有没有改坏。（第 6 章） |
| 产品形态 | 系统长什么样给人用：网站、小程序、App、管理后台、接口服务，或者几种组合。（第 2 章） |
| 冲突 | 两条分支改了同一处代码，Git 不知道该保留哪个，要人来决定。（第 7、13 章） |

## D

| 术语 | 解释 |
|---|---|
| DAG（依赖图） | 任务之间谁依赖谁的关系图，用来决定先做什么后做什么。（第 4 章） |
| DNS（域名解析） | 把域名翻译成服务器地址的系统。改了解析要等一段时间才生效，本地还可能有旧缓存。（第 7、13 章） |
| Docker | 把程序和它需要的运行环境打包在一起的工具，打好的包叫镜像，运行起来叫容器。到哪台服务器都能用同样的方式跑。（第 7 章） |
| Docker Compose | 用一个配置文件同时启动多个容器，比如应用、数据库、缓存一起启动。（第 7 章） |
| 定金 / 尾款 | 开工前先付的一部分钱，和验收通过后付的剩余部分。（第 12 章） |
| 端口 | 一台服务器上区分不同程序的编号。比如应用在 3000 端口，网页默认走 80 和 443 端口。（第 13 章） |
| 对账 | 定期把系统里的订单和支付平台的账单逐笔核对，确认钱对得上。（第 9 章） |

## F

| 术语 | 解释 |
|---|---|
| 反向代理 | 站在服务器门口的一层程序，外部请求先到它，再由它转给后面的应用。HTTPS 证书通常也装在它这里。常见的有 Nginx。（第 7、13 章） |
| 分支 | 从某个时间点分出来的一条代码路线，用来单独做一项功能或修一个问题，做完再合回主线。（第 7 章） |
| 分支保护 | GitHub 上守住主线的规则，比如必须经过 PR 和检查才能合并，不许直接改。（第 7 章） |
| 复盘 | 事情结束后写下发生了什么、证据是什么、哪些判断被推翻、怎么防止再发生。（第 13 章） |
| 服务端 / 后端 | 跑在服务器上、用户看不到的那部分程序，负责算钱、存数据、校验权限。（第 3、9 章） |
| 复现 | 按同样的步骤让问题再出现一次。复现不了的问题，很难确认修好了没有。（第 13 章） |

## G

| 术语 | 解释 |
|---|---|
| Git | 记录代码每一次改动的工具，可以随时退回之前的任何一个版本。（第 7 章） |
| GitHub | 托管 Git 仓库的网站，也是协作的地方：存代码、提 issue、开 PR、跑自动检查。（第 7 章） |
| GitHub Actions | GitHub 自带的自动化工具，可以在提交代码后自动跑测试、自动部署。（第 7 章） |
| 告警 | 系统出问题时自动发通知给人，目标是比用户先知道。（第 8 章） |
| 根因 | 问题最底层的原因。页面上看到的现象不等于根因。（第 13 章） |

## H

| 术语 | 解释 |
|---|---|
| HTTPS | 加密的网页访问方式，网址前面有锁。需要给域名申请证书。（第 7 章） |
| 合并 | 把一条分支的改动并进另一条分支，通常是并回主线。（第 7 章） |
| 缓存 | 把常用的数据临时放在更快的地方，下次直接取。Redis 常用来做缓存。也指浏览器或电脑里留着的旧结果。（第 8、13 章） |
| 环境（本地 / 测试 / 生产） | 同一套代码跑在不同地方：本地是你自己的电脑，测试环境给内部试用，生产环境给真实用户用。三者的数据库和密钥要分开。（第 7 章） |
| 环境变量 | 不写在代码里、在运行时从外部传给程序的配置，比如数据库地址、密钥。换一个环境只需要换一组变量。（第 7 章） |
| 回调 | 支付平台在用户付完钱后，主动通知你的系统「这笔已付」。回调可能丢，也可能重复到达。（第 9 章） |
| 回滚 | 新版本出问题时，退回到上一个能用的版本。（第 7、8 章） |

## I

| 术语 | 解释 |
|---|---|
| issue | GitHub 上的一张问题单或任务单，记录一个 bug、一个需求或一项讨论。（第 4 章、附录 B） |

## J

| 术语 | 解释 |
|---|---|
| 健康检查 | 一个专门用来回答「系统活着没有」的地址。浅检查只看应用，深检查还看数据库和缓存。（第 8、14 章） |
| 鉴权 | 每次请求时，在服务端确认「你是谁、有没有权限做这件事」。只在前端藏按钮不算鉴权。（第 10 章） |
| 交付物 | 交给甲方的全部东西：线上地址、账号、代码、说明文档、验收清单、维护约定等。（第 14 章） |
| 技术栈 | 一个项目用到的全部技术组合：前端用什么、后端用什么、数据库用什么、部署在哪。（第 3 章） |
| 角色 | 按职责划分的用户类型，比如店长、店员，不同角色能看、能改的东西不同。（第 2、10 章） |

## K

| 术语 | 解释 |
|---|---|
| 开源 | 代码公开、任何人都能看、能提修改建议的项目。（附录 B） |
| 框架 | 别人写好的一套基础代码和规矩，你在上面填自己的业务，不用从零开始。（第 3 章） |

## L

| 术语 | 解释 |
|---|---|
| 乐观锁 | 防止两个人同时改同一条数据互相覆盖的办法：改之前记下版本号，保存时版本号变了就拒绝，让后来的人刷新重试。（第 8 章） |
| 里程碑 | 排期里的阶段节点，每个节点交出一个能看见的东西，比如第一版、验收版。（第 12 章） |

## M

| 术语 | 解释 |
|---|---|
| main（主线） | 仓库默认的那条主分支，代表大家认可的最新代码。以 GitHub 上的为准，电脑里的可能是旧的。（第 7、13 章） |
| 冒烟测试 | 发布后快速点一遍最关键的功能，确认没有一上线就坏。（第 7 章） |
| 幂等 | 同一个操作做一次和做多次，结果一样。比如同一笔支付回调到两次，只记一次账。（第 9 章） |
| 密钥 | 证明「我有权调用某个服务」的一串字符，比如数据库密码、支付密钥。不能进代码仓库。（第 7 章） |

## N

| 术语 | 解释 |
|---|---|
| Nginx | 最常用的反向代理和网页服务器软件之一。（第 7、13 章） |

## P

| 术语 | 解释 |
|---|---|
| PR（Pull Request，合并请求） | 把一条分支的改动拿出来，请别人审核、跑检查，再决定要不要合进主线。（第 5、7 章） |

## Q

| 术语 | 解释 |
|---|---|
| 前端 | 用户直接看到和操作的那部分：网页、小程序页面、App 界面。（第 3 章） |
| 迁移（数据库迁移） | 用脚本记录并执行数据库结构的每一次修改，可以追溯、可以在各个环境重复执行。不直接手改生产表。（第 8、14 章） |
| 权限 | 规定谁能看什么、改什么。（第 10 章） |

## R

| 术语 | 解释 |
|---|---|
| RBAC（基于角色的权限控制） | 先给角色分配权限，再把角色分给人。换岗只要换角色，不用逐个改权限。（第 10 章） |
| README | 仓库首页的说明文件，写项目是什么、怎么跑起来。（第 7、14 章） |
| rebase | 把一条分支挪到最新的主线上，重新接一遍。什么时候做，要听负责合并的人安排。（第 13 章） |
| Redis | 一种很快的数据存储，常用来做缓存和防止并发冲突。（第 8 章） |
| RPO / RTO | 恢复数据时的两个指标：RPO 是最多会丢多少时间的数据，RTO 是恢复要花多久。（第 8 章） |
| 日志 | 程序运行时留下的记录：什么时候、谁、做了什么、出了什么错。排查问题首先看它。（第 8、13 章） |

## S

| 术语 | 解释 |
|---|---|
| Secret | GitHub 等平台上专门存密钥的地方，自动化流程可以读取，但页面和日志里不显示。（第 7 章） |
| seed（种子数据） | 初始化时写进数据库的示例数据，让系统一跑起来就有东西可看。（第 3、14 章） |
| SSH | 远程登录服务器、在上面执行命令的方式。（第 13 章） |
| 审计日志 / 操作记录 | 专门记录关键操作的日志：谁、什么时候、改了什么、改之前是什么。出了事用来追责。（第 10 章） |
| 事务 | 把几步数据库操作绑成一组，要么全部成功，要么全部撤销，不会只做一半。（第 9、10 章） |
| 数据库 | 系统长期存放数据的地方，比如订单、菜单、顾客。（第 2、3 章） |
| 四个层次 | 本书对项目成熟度的划分：Demo（自己电脑上能演示）、完整（功能齐、能上线）、生产级（上线后一直稳定跑）、商业级（有人付钱用，出错有人追责）。（第 0 章） |

## T

| 术语 | 解释 |
|---|---|
| 提交（commit） | Git 里的一个存档点，记录这一次改了哪些文件、为什么改。（第 7 章） |
| 脱敏 | 显示个人信息时隐去一部分，比如手机号只显示前三位和后四位。（第 10 章） |

## W

| 术语 | 解释 |
|---|---|
| Webhook | 一个系统发生某件事时，主动向另一个系统的地址发通知。支付回调就是一种 Webhook。（第 9 章） |
| worktree | Git 的功能，让同一个仓库在电脑里同时开多个工作目录，每个目录检出不同分支。目录名不代表里面是哪个分支。（第 13 章） |
| 维护约定 | 上线后维护的书面约定：维护什么、不维护什么、多久响应、多少钱。（第 14 章） |

## X

| 术语 | 解释 |
|---|---|
| 限流 | 限制同一时间进来的请求数量，防止系统被突然的流量冲垮。（第 8 章） |
| 小程序 | 运行在微信等平台里的轻量应用，不用单独下载安装，上线要过平台审核。（第 2、10 章） |
| 需求变更 | 开工后对范围的修改。要记录、评估影响、书面确认后再做。（第 12 章） |

## Y

| 术语 | 解释 |
|---|---|
| 压测（压力测试） | 模拟很多人同时使用，看系统能扛多少、在哪里先撑不住。（第 8 章） |
| 验签 | 收到支付平台的通知时，校验它确实来自支付平台、内容没被篡改。（第 9 章） |
| 验收 | 甲方按事先约定的清单逐条检查，确认交付的东西达到要求。（第 14 章） |
| 域名 | 网站的名字，比如一串以 .com 结尾的地址，通过 DNS 指向服务器。（第 7 章） |
| 越权 | 用户做了自己权限之外的事，比如店员改了价格，或者看到了别人的订单。（第 10 章） |
| 约束理论 | 一条流程的整体速度，取决于当前最慢的那个环节。提速要先找到并解决它。（第 1、14 章） |
| 运维手册 | 写给出了问题的人看的文档：系统在哪、怎么看状态、怎么发布、回滚、恢复，常见故障怎么处理。（第 14 章） |

## Z

| 术语 | 解释 |
|---|---|
| 证据边界 | 下结论前写清楚的两张清单：目前能确认什么，不能确认什么。（第 13 章） |
| 状态机 | 规定一个对象有哪些状态、每个状态能跳到哪些状态。比如订单只能从制作中到待取餐，不能从待接单直接跳到已完成。（第 2 章） |
