# 第 5 章　管住 AI：规则、工作流和审查

这一章是初稿，还会修改。
:::

![会用工具](/book/ch05-1.webp)

## 本章要回答

为什么同样的工具有人用得很笨；规则文件怎么写；工作流为什么比提示词重要；怎么审 AI 交回来的东西。

## 示例项目推进到哪

写一份 餐厅后台的 AGENTS.md。

读完这一章，你能做成三件事：给餐厅后台写一份规则文件，让 AI 每次开工前先读它；把一次改动按固定的工作流交给 AI；AI 交回结果时，用四个问题审它：任务说清没有，它改了什么，结果对不对，有没有越界。

本章默认你已经学过 [GitHub 入门小课](/github/)。分支、提交、PR 怎么操作，小课里都有，这里只讲判断。

## 同一个工具，为什么有人用得很笨

我跟一个电商老板聊过 Codex。他说豆包都比 Codex 好用。后来我看了他的使用过程。拖慢他的是工具没调好，模型本身没什么问题。

有一次线下活动，大家做同样的网站。我用 5 分钟部署好了。有人花了半个小时还没弄完。我把大家的使用过程拉出来对比，卡住的地方大多是同几处：

| 卡在哪 | 表现 | 我的做法 |
|---|---|---|
| 权限 | 改个文件、跑个命令，都停下来等你点允许 | 在确认过的项目里放开权限，让它连续做完改代码、跑测试、部署 |
| 插话 | 任务跑到一半，发现方向错了，插不上话 | 设成随时能插话的模式，发现它理解错了立刻叫停 |
| 会话 | 一个对话聊太久，塞满旧需求、废弃方案和报错 | 卡住就开一个干净的新会话，把要紧的背景带过去 |
| 网络 | 反复显示「正在重新连接」 | 先查网络、代理和服务商，别先怪模型 |
| 找回旧方案 | 不记得上次做到哪、怎么解决的 | 用任务搜索翻项目名、报错词 |

第一项要多说一句。放开权限的前提，是改坏了能退回来：项目在 Git 里，改动在分支上做（见 [分支和 PR](/github/branch-and-pr)），规则文件写清了哪些命令不许用。三样都有，放开权限才安全。缺一样，就别放开。

模型之间确实有差距。一位在大厂做模型相关工作的朋友跟我说，同一家公司的模型，不同业务会按任务挑不同尺寸。简单、重复、出错代价低的任务，用小而便宜的模型；多步推理、要读大量代码的任务，用强的模型。这个判断要在任务说清楚之后才能做。任务没说清，换哪个模型都在猜。

所以觉得 AI 笨的时候，按这个顺序查：工作台设置好了没有，任务说清了没有，最后才查模型够不够强。

## 工作流比提示词值钱

我看过一个工程师的案例。他让 AI 读一套 C++ 代码，生成详细设计文档。第一次，他把整件事交给一个 AI，拿回来一份粗糙的框架。第二次他没换模型，只改了分工：一个 AI 做规划，几个 AI 分头研究不同模块，最后一个 AI 汇总和检查。按他的记录，第二次的产出体量是第一次的七倍多。

体量大，不等于质量高七倍。但模型没换，只换了分工，结果就明显不同。

提示词管的是一轮对话。工作流管的是整件事：先做什么，后做什么，谁来检查。复杂任务都可以拆成三步：说清目标，拆开任务，单独验收。

落到写代码上，我给餐厅后台用的工作流是这样：

1. AI 读规则文件和相关代码。
2. AI 用自己的话复述任务，列出要改哪些文件、不改什么、怎么验证。你确认后它再动手。
3. AI 在分支上小步改，每改完一块跑一次验证。
4. AI 交回一份报告：改了哪些文件，跑了哪些命令，结果是什么，哪些没验证。
5. 你按本章后面的四个问题审。通过了才合并。

第 2 步最容易被跳过，因为它看起来慢。可最浪费时间的情况，是 AI 已经写了二十分钟，你才发现它理解的根本不是你要的东西。

第 1 步和第 4 步每次都一样。每次都在对话里重复，迟早会漏。把它们写进规则文件。

## 规则文件：把规矩写一次

规则文件是放在项目根目录的一份说明，AI 每次开工前会先读它。不同工具认的文件名不同，常见的是 `AGENTS.md` 和 `CLAUDE.md`。写一次，之后每个任务都受它约束。

做餐厅后台时，题目明确要求重度使用 AI，评分也看你怎么管住 AI。我写的 `AGENTS.md` 有十几节。按作用归一下，是这几类：

| 类别 | 写了什么 |
|---|---|
| 开工前读什么 | 先读这份规则，再读题目原文；子目录有自己的规则时，动那个目录前先读 |
| 事实以哪里为准 | 目录结构是固定的；数据以数据表定义为准，接口以后端生成的接口描述为准，前端的类型和请求代码从接口描述自动生成，不手写 |
| 硬性禁止 | 不许换掉指定的技术栈；不许让前端决定订单总价；不许做「传什么状态就改成什么状态」的接口；不许接受售罄的菜；不许为了消掉类型报错去改自动生成的文件；不许做和题目无关的大改 |
| 谁负责什么 | 后端负责存数据、校验、算金额、查菜能不能卖、推进订单状态；前端负责展示和交互 |
| 怎么证明做完了 | 交付前跑接口生成、类型检查、测试和代码检查；后端测试必须覆盖五种下单行为；证明不了，就写清哪条命令失败、为什么、哪些没验证 |
| Git 规矩 | 每做完一件完整的事就提交；提交前看改动，只提交本次相关的文件；不许用会丢数据的命令 |
| 安全 | 不打印密钥；不提交 `.env` 和数据库密码；新加的依赖要说得出用途 |
| 交付清单 | 最后逐项对照：几个页面都能用，下单能走通，测试覆盖订单规则，README 写清了怎么跑、做了哪些取舍 |

写的时候我有几条判断。你写自己的规则文件时也用得上。

**禁止项写 AI 最容易犯、代价又最高的错。** 「让前端决定总价」是一个例子。AI 做下单页时，在页面上把价格加起来提交给后端，是最省事的写法。这样一来，谁改一下请求里的数字，就能让一桌菜只收一块钱。「为了消掉类型报错去改生成文件」也是。AI 遇到报错，倾向于在最近的地方改。生成文件下次一重新生成，改动就没了，问题还在。

**写清事实以哪里为准。** 一个项目里，同一样东西常有好几份：数据库里一份，接口里一份，前端又一份。AI 不知道哪份说了算，就会改错地方。规则里写一句「数据以数据表定义为准，前端类型从接口自动生成」，它就知道改一个字段要从哪里改起。

**写清怎么证明。** 只写「改完要测试」不够。要写出具体命令，写出哪些行为必须有测试。还要写一条：证明不了的时候，说清哪些没验证。这一条最要紧。没有它，测试跑不起来时，AI 照样会告诉你「已完成」。

**Git 规矩用小课的。** [让 AI 操作 GitHub](/github/ai) 那一课给了一段现成的 Git 规则，直接放进去。

**规则不用一次写全。** AI 犯了一次值得记住的错，就补一条。

下面是一份可以直接用的起点。存成项目根目录的 `AGENTS.md`，再按你的项目改：

```markdown
# 餐厅后台规则

## 开工前
- 先读本文件和 README。改某个目录前，先读那个目录里的 AGENTS.md（如果有）。
- 不确定某个库怎么用时，先查官方文档或源码，不要凭印象写。

## 以哪里为准
- 数据结构以后端的数据表定义为准。
- 接口以后端生成的接口描述为准。前端的类型和请求代码从它自动生成，不手写。

## 不许做
- 不许让前端决定订单金额。金额由后端按菜单价格计算。
- 不许提供可以把订单改成任意状态的接口。状态只能按规定的顺序推进。
- 不许接受已售罄的菜品下单。
- 不许修改自动生成的文件来消除报错，要改生成它的源头。
- 不许做和当前任务无关的重构或改名。
- 不许为了让测试通过去删测试或放宽断言。

## 分工
- 后端负责：存储、校验、金额计算、可售检查、订单状态推进。
- 前端负责：展示、交互、提示信息。

## 做完要证明
- 交付前运行类型检查、测试、代码检查、构建。命令见 README。
- 改了前端，就在浏览器里走一遍改到的页面。
- 交回时写清：改了哪些文件；跑了哪些命令、结果是什么；哪些没验证、为什么。

## Git
- （把 GitHub 入门小课第 6 课的规则放在这里）

## 安全
- 不打印、不提交任何密钥和 .env 文件。
- 新加依赖前说明用途。
```

## 让代码好找、好改

规则文件告诉 AI 规矩。代码本身的结构，决定它守不守得住。

AI 进到一个项目，和新人接手代码一样，要先找入口，看懂哪块负责什么。它最怕两件事：找不到该改哪里；改了一处，不知道会影响哪里。

三条老原则正好对着这两件事：

- **高内聚**：相关的逻辑放在一起。下单相关的规则都在下单模块里，AI 一找就到。
- **低耦合**：模块之间少牵连。页面不直接查数据库，改页面就不会误伤数据。
- **单一职责**：一个函数只做一类事。叫 `handleData`、`processAll` 的函数，往往什么都做，改一处牵一片。

餐厅后台按这个分了层。接口入口只做三件事：读参数，调业务函数，返回结果。算金额、判断状态能不能变这些业务规则，放在单独的领域模块里，并且有测试。数据读写单独一层。要改金额规则，AI 直接去领域模块，改完跑那一组测试。

分层不用你自己设计，交给 AI。你检查两件事：从目录名和文件名，能不能猜到要改的地方；改完以后，有没有测试或构建能证明没误伤别处。两件都做不到，先让 AI 整理结构，再加功能。细节见 [对 AI 友好的代码](/guide/ai-friendly-code)。

## 一次任务怎么交

有了规则文件，每次派活只写这次特有的东西：目标、范围、不做什么、怎么算做完。

下面是给餐厅后台加「最低下单金额」时，我会发给 AI 的话：

```text
任务：设置里加「最低下单金额」，菜品小计低于它时，后端拒绝下单。

目标：餐厅能在设置页填一个最低下单金额，默认 0，表示不限制。下单时菜品小计低于这个金额，后端拒绝，返回明确的错误码；前端提示「未达到最低下单金额」。
范围：设置的数据和接口加一个字段；下单的业务函数加一条检查；设置页加一个输入框；下单表单显示这个错误。
不做：不改税率和金额的算法；不改订单状态规则；不调页面样式。
做完的标准：
1. 最低金额设为 50 元：下一单 28 元的，被拒绝，提示清楚；下一单 56 元的，成功。
2. 最低金额为 0 时，行为和现在完全一样。
3. 新规则有后端测试；原有测试全部通过；类型检查和构建通过。

先按 AGENTS.md 读相关代码，用你的话复述任务，列出要改的文件和验证方法。我确认后再动手。
```

AI 干活的时候，你不用盯着每一行。但要做两件事：

- **看到方向错了，立刻叫停。** 最怕它沿着错误方向勤快了十分钟。直接说：「停，这个接口别重写，先查现有实现。」
- **会话乱了就换。** 一个会话里堆了三个废弃方案和一堆旧报错，它会越来越像在猜。开一个新会话，把任务和规则文件带过去。

让 AI 查问题时，给它证据，别给情绪。「还是不行，你再改改」没有用。要说清：哪个页面，按什么顺序做了什么，实际结果是什么，你期待什么，报错原文是什么。再加一句：先定位原因，只修这一个问题。这套方法第 13 章（[出事了先找证据](/book/ch13)）会细讲。

## 怎么审 AI 交回来的东西

AI 说「完成了」，只能说明它执行过。能不能合进主线，用四个问题审。

**1. 任务说清没有。**

这一问在动手前就要问。看 AI 的复述：它说的目标、范围、不做的事，和你想的一样吗？它列的要改的文件，和任务对得上吗？对不上，先改任务，别让它开工。很多返工，根子都在这一步。

**2. 它改了什么。**

打开 PR 的改动页面，先看文件清单，再看内容。重点看这几类：

- 有没有和任务无关的文件。
- 有没有改自动生成的文件、锁文件、配置文件。
- 有没有加新依赖。
- 有没有删东西，尤其是测试。
- 测试里的预期值有没有被改。

你不需要读懂每一行代码。文件清单和任务对不上，就足够打回去。

**3. 结果对不对。**

别看 AI 的结论，看证据：它跑了哪些命令，输出是什么，检查是不是全绿。然后你自己走一遍改到的功能。最低下单金额的例子，就是设一个最低金额，先下一单低于它的，再下一单高于它的。什么叫做完、测试先测哪里，下一章（[什么叫做完了](/book/ch06)）专门讲。

**4. 有没有越界。**

拿规则文件的「不许做」逐条对一遍。再看几样规则里不一定写到的：有没有碰密钥和环境配置；有没有跨层调用，比如页面直接查数据库；有没有动别的任务的代码。

小课第 6 课讲了在 PR 页面上看哪四处。这四个问题讲的是，看的时候要判断什么。

## 判断力从哪来

很多人说，有了 AI，人只需要负责判断。可判断力从哪来？你不知道 AI 会在哪里出错，审它的时候，就只能一路点同意。

上面规则文件里的每一条禁止项，都是一次具体的判断：金额不能让前端说了算，状态不能随便改，生成文件不能手改。这些判断来自你知道业务里什么东西出错代价最高，和用哪个工具无关。第 2 章（[先弄清业务怎么转](/book/ch02)）讲的业务流程，就是这些判断的来源。

会用 Claude Code 和 Codex，已经很难证明一个人的价值。如果你只能执行，决定不了做什么、什么算完成，你就成了 AI 时代的力工：别人定义问题，AI 给出实现，你负责修报错和提交。

AI 可以写代码、写测试、查问题。系统出错以后的后果，它替你担不了。规则文件、工作流和审查，都是为了让你担得起这个后果。

## 本章做完的样子

- 餐厅后台根目录有一份 `AGENTS.md`，写了以哪里为准、不许做什么、前后端分工、怎么证明做完、Git 规矩和安全要求。
- 你用本章的派活模板交了一个任务。AI 先复述，你确认后它才动手。
- 这个任务的 PR，你按四个问题审过：看过文件清单和检查结果，亲手走过一遍改到的功能。
- AI 犯过的错里，值得记住的已经补进规则文件。

## 这一步谁来做

| 交给 AI 的 | 你要判断和验收的 |
|---|---|
| 写代码、改代码、写测试、查问题。 | 任务说清没有；它改了什么；结果对不对；有没有越界。 |
