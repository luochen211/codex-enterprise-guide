## 本章要回答

开源 issue、真实商单。

## 先说结论

读完这本书，下一步是找一个真实项目，把书里的流程实际走一遍。有两条路：去开源项目修一个 issue，或者接一单真实的小商单。前者有人审你的代码，后者有人付钱、你要担责。两条可以先后走，也可以同时走。

## 为什么别再自己憋一个项目

我以前当助教时，经常有计算机专业的学生问：老师，我没项目，简历写什么？

很多人的做法是自己憋一个：校园二手平台、天气 App、图书管理系统、AI 简历助手。这些项目能训练基础，但缺少真实世界的压力。没人真的用，没人提 issue，没人审你的代码，没人要求你兼容旧版本，也没人关心你的改动会不会影响别的用户。

它能证明你会搭东西，很难证明你能进入一个真实团队协作。而工作以后，你接手的往往是一个已经运行很久的系统：要读别人的代码，理解别人的设计，修一个具体的 bug，补一段文档，加一个测试，还要保证没把别的地方弄坏。这正是第 13 章讲的「接手别人的代码」。

## 路一：去开源项目修一个 issue

GitHub 上每天都有大量真实问题没人处理。入口可以很小：

- 文档过期了，你可以修；
- 安装步骤跑不通，你可以查；
- 测试失败了，你可以补；
- 新手教程看不懂，你可以改；
- 一个 issue 半年没人处理，你可以试着接手。

找的时候，先从你自己用过的工具和库开始，你知道它该是什么样。很多项目会给适合新人的 issue 打上 `good first issue` 或 `help wanted` 标签，可以按标签筛。

走一遍的步骤：

1. **先读规矩。** 看项目的贡献说明和最近合并的几个 PR，了解它要求什么格式、跑什么检查。
2. **挑一个你能看懂的问题。** 在 issue 下留言说你想处理，避免和别人撞车。
3. **让 AI 带你读仓库。** 项目怎么跑起来，问题对应哪段代码。
4. **复现。** 先在自己电脑上让问题出现。复现不了，就别急着改。
5. **修改并补测试。** 一个 PR 只做一件事。
6. **提 PR。** 写清改了什么、为什么改、怎么验证的。
7. **回应 review。** 维护者提的意见逐条回复，改完再请他看。

给 AI 的任务可以这样写：

```text
我想处理这个开源项目的 issue：[issue 链接或内容]。
请先不要改代码，按顺序做：
1. 读 README 和贡献说明，告诉我怎么在本机跑起来、提交前要跑哪些检查；
2. 找出这个问题最可能对应的文件和函数，说明理由；
3. 给出复现步骤。
等我确认复现成功，再一起改。
```

AI 能帮你理解代码，结果由你负责。问题能不能复现，修改有没有生效，测试有没有通过，review 有没有处理完，这些都要你自己确认。

有一条礼仪要记住：维护者有自己的节奏。PR 显示落后或冲突，先别急着 rebase，也别反复催；轮到它的时候，维护者会告诉你要做什么。我自己在这上面犯过错，经过写在 [/cases/pr-rebase-timing-incident](/cases/pr-rebase-timing-incident)。

一条 PR 从提交到合并，会留下几种可以验证的记录：你怎么理解问题，怎么完成修改，怎么补测试，怎么回应 review。写进简历时，直接附上 PR 链接。

GitHub 的基本操作不熟，先看 [/github/](/github/) 和 [/guide/github-workflow](/guide/github-workflow)。

## 路二：接一单真实的小商单

开源练的是协作和读别人的代码。商单练的是另一半：问清需求、报价、交付、验收、收钱。

第一单不要找大的。找一个边界清楚、几天内能做完的问题，功能不用多，技术也不用炫。重点是完整走一遍：需求确认、报价、开发、验收、复盘。

开工前至少写清四件事：

- 这次具体解决什么问题；
- 包含哪些功能，哪些暂时不做；
- 最后交付什么；
- 对方根据什么判断完成。

报价单、变更单怎么写，见[第 12 章](/book/ch12)。交付和验收怎么做，见[第 14 章](/book/ch14)。上线前用附录 A 过一遍。

第一单的钱可以不多，但它要能结束。从第二单开始，再用第 12 章的四条标准筛：这笔钱是不是靠你一直在线，是不是做得越多越便宜，是不是切碎你的时间，能不能留下案例。

做完以后，把需求、方案、交付和踩过的坑整理成一个案例。下次别人问你做过什么，你能讲清楚：客户当时遇到什么问题，你怎么拆需求，最后交付了什么，中间有什么风险，用什么证据证明它已经完成。

## 两条路怎么配合

| | 开源 issue | 真实商单 |
|---|---|---|
| 练什么 | 读别人的代码、按规矩协作、接受 review | 问需求、报价、交付、验收 |
| 谁来验收 | 项目维护者 | 付钱的客户 |
| 留下什么 | 被合并的 PR 链接 | 案例、报价单和验收清单模板 |
| 风险 | 低，最多不被合并 | 有钱有责任，边界没写清会被拖住 |

两条路留下的东西不一样，但检验的是同一件事：你能不能把一个真实问题，变成别人愿意接受的结果。
