# 第 14 章　交付、验收与维护

## 本章要回答

交付要交什么；甲方怎么验收；上线之后谁来管、怎么收维护费。

## 示例项目推进到哪

交付清单、运维手册和一份维护约定。

## 先说结论

代码写完、线上能打开，离交付还差一段。交付的终点是：甲方能自己照着用起来；出了问题，知道找谁、多久有回应；上线以后的维护范围和费用，双方都认过。

读完你能做三件事：

- 列出一份交付清单，知道要交哪些东西；
- 写一份甲方能逐条打勾的验收清单，组织一次验收；
- 写一份维护约定，说清上线以后谁来管、管什么、怎么收费。

## 七天做完，一个月才用起来

我现在用 AI，七天能把一个项目做到能运行、能交付的状态。同样的项目进入成熟企业，从代码完成到正式进入业务，通常还要一个月以上。

代码完成以后，甲方还要审：业务流程对不对，权限和数据有没有问题，能不能接进现有系统，谁批准上线，最终使用的部门要验收。这些等待、确认和修改，不会随着代码一起消失。

假设一个项目原来要三十天，其中七天开发，二十三天等待、审查和验收。AI 把开发再压到三天，整个项目也只短了四天。你一天能交出三个版本，甲方一周只审得完一个，多出来的版本只会停在流程里排队。

管理学里有个约束理论，讲的就是这件事：一条交付链的速度，取决于当前最慢的那个环节。开发慢的时候，代码是瓶颈。AI 把开发提速以后，瓶颈移到了需求确认、审查和签字上。

甲方的审查有它的道理。企业系统一进生产环境，影响的是客户数据、订单、资金和员工权限。「我这里已经跑通」替代不了业务负责人、安全人员和最终使用者的判断。

作为交付方，你能做的是让审查走得快一点：审查要用的材料提前备齐，不让对方反复来要。测试证据、变更说明、风险清单、验收文档，这些 AI 都能帮你整理。材料一次给齐，审查就少一轮来回。

所以这一章讲的交付清单、验收清单和运维手册，直接决定项目多久能用起来，也决定你多久能收到尾款。

## 交付要交什么

餐厅后台这道面试题本身给了一份最小的交付清单，要求提交：

- 代码仓库；
- 本地运行说明；
- 初始化示例数据的说明；
- 架构决策的简短说明；
- 取舍和未完成部分的简短说明；
- 可选：一段演示录屏。

这份清单是给评审者看的：让他能跑起来，看懂为什么这么做，知道哪里没做完。第五条特别值得学。主动写出哪里没做完，比让对方自己发现可信得多。

商用交付面向甲方，要多交几样东西：能用、能管、出了事能处理。我给餐厅后台列的商用交付清单如下。

| 交付物 | 给谁 | 内容 |
|---|---|---|
| 线上地址和账号 | 老板、店员 | 正式域名，店长和店员账号，首次登录改密码 |
| 代码仓库 | 甲方或接手的技术人员 | 移交到甲方自己的账号下，或者给甲方管理员权限 |
| 运行说明 | 技术人员 | 怎么在一台新电脑上跑起来，怎么初始化数据 |
| 部署说明 | 技术人员 | 部署在哪，怎么发布新版本，怎么回滚 |
| 环境变量清单 | 技术人员 | 只列名字和用途，不写值；值用安全的方式单独交给甲方 |
| 第三方账号清单 | 老板 | 服务器、域名、数据库、支付等账号在谁名下，每月多少钱，什么时候续费 |
| 使用说明 | 店员 | 怎么下单、怎么改菜单，最好配截图 |
| 运维手册 | 技术人员，或者你自己 | 出了问题怎么查、怎么恢复 |
| 验收清单 | 老板 | 逐条打勾、签字 |
| 已知限制 | 老板 | 这一期没做的，做了但有边界的 |
| 维护约定 | 双方 | 上线以后谁管、管什么、多少钱 |

第三方账号清单最容易漏。很多项目上线时，服务器和域名是开发者用自己的账号买的。合作结束以后，续费提醒发到别人手机上，域名到期了甲方都不知道。账号尽量一开始就开在甲方名下。开在你名下的，交付时列清楚，约好怎么转。

陪玩系统的 README 里写过一份生产交付要求，可以当成上线前的底线：

- 全站 HTTPS，通过反向代理统一接入；
- 生产环境有真实的登录、角色权限和服务端鉴权；
- 超级管理员后台至少再加一层保护；
- 数据库改结构走迁移脚本，不直接手改生产表；
- 支付回调用生产域名，回调要验签、留日志；
- 上线前配好日志、监控、备份、告警、发布记录和回滚方案；
- 有健康检查接口：浅检查看应用活着没有，深检查看数据库和缓存通不通。

这几条在第 7 到第 10 章分别讲过。交付时，把每一条的证据附上：截图、链接或命令输出。

## 验收：用业务的话写，让甲方自己点

验收清单最常见的问题是用技术语言写，比如「订单接口返回 200」。老板看不懂，也没法自己验。

验收清单要用业务的话写，写成一个个甲方能自己动手做的操作。陪玩系统做完一个月的修改以后，我整理过一份 26 条的验收清单，按角色排，其中几条是这样的：

- 顾客进入小程序后，可以查看首页、公告、订单和个人中心；
- 陪玩可以提交入驻申请，申请时需要选择分组；
- 管理员可以查看陪玩申请详情并审核；
- 审核通过的陪玩可以进入陪玩中心；
- 接待可以代客建单；
- 未审核的陪玩不能进入陪玩功能区；
- 未授权的接待不能进入接待功能区。

注意最后两条。验收既要验「能做」，也要验「不能做」。权限有没有收住，只有换一个没权限的身份去试才知道。

同一个项目的需求确认文件开头写着一句话：未在本文档中确认的功能，不作为本次交付验收内容。这句话把验收范围和需求范围绑在了一起。验收时对方说「我还以为有某某功能」，你可以指着这份文件说：这个不在本期范围，可以按变更另报。[第 12 章](/book/ch12)讲的变更流程，最后就落在这里。

餐厅后台的验收清单可以这样写：

```text
餐厅后台第一期验收清单

菜单
□ 店长新增一道菜并填写价格，店员下单时能选到
□ 店长把一道菜设为停售，下单时选不到
□ 已经被下过单的菜不能删除，只能停售

订单
□ 店员为一位顾客下两份同一道菜，订单金额 = 单价 × 2 + 税
□ 订单从待接单依次推进到已完成，每一步都成功
□ 已完成的订单不能再改回制作中
□ 完成前的任一状态都可以取消

顾客
□ 顾客下单后，顾客页里的消费金额和下单次数随之增加

设置
□ 关闭营业状态后，无法下新单
□ 修改税率后，新订单按新税率算，旧订单金额不变

经营首页
□ 当天的订单在首页能看到，收入和订单量与订单列表加总一致

权限
□ 店员账号进不了设置页，也改不了菜品价格
□ 退出登录后，直接打开后台地址会跳到登录页

运维
□ 甲方的技术人员照运行说明，在一台新电脑上跑起来
□ 演示一次从备份恢复数据

甲方确认人：　　　　日期：
```

每一条都是一个能当场操作的动作，结果对就打勾。验收最好约甲方一起在线上环境做，你在旁边看，不要替他点。他自己点过一遍，后面的培训就省了一半。

清单全部打勾、对方签字，尾款节点就到了。签字之前说的「差不多了」不算。

## 运维手册：让别人半夜也能处理

运维手册写给出了问题的那个人看。这个人可能是甲方的技术员，可能是接手的人，也可能是半年以后已经忘了细节的你自己。

它至少回答这几件事：

1. **系统由哪几部分组成，各在哪里。** 前端在哪发布，后端在哪运行，数据库在哪。
2. **怎么判断它活着。** 健康检查的地址，正常时返回什么。
3. **怎么发布新版本，怎么回滚到上一版。** 写成能照着做的步骤。
4. **日志在哪看。**
5. **备份在哪，怎么恢复。** 恢复步骤要真的演练过，见[第 8 章](/book/ch08)。
6. **常见故障怎么处理。** 每条写现象、先查什么、怎么处理。[第 13 章](/book/ch13)的 502 就可以写成一条：服务器本机健康检查正常、域名访问 502，先查代理的转发目标和应用的绑定地址。
7. **密钥怎么换。** 有哪些密钥，在哪里改，改完要重启什么。
8. **出了问题找谁。** 联系方式和响应时间，和维护约定对上。

运维手册的验收只有一条：让一个没参与开发的人照着做一遍。他卡住的地方，就是手册要补的地方。

## 维护：管什么、多快响应、怎么收钱

上线以后，系统还会出问题，甲方还会提要求。不提前约定，维护就会变成随叫随到、没完没了。

第 12 章讲过怎么判断低水平的钱：高度依赖你本人一直在线，这笔钱租的是你的待命状态。维护最容易滑成这种钱。所以维护约定要把「待命」变成有边界的服务。

一份维护约定至少写清这几项：

| 项目 | 要写清什么 |
|---|---|
| 期限 | 从哪天到哪天，到期怎么续 |
| 包含什么 | 已交付范围内的缺陷修复，服务器和证书到期提醒，依赖的安全更新，定期检查备份 |
| 不包含什么 | 新功能、改业务规则、界面改版、第三方平台政策变化带来的大改，这些走变更另报价 |
| 响应时间 | 按严重程度分级。例如不能下单、数据出错算紧急；某个页面显示错位算一般。每一级写多久回应、多久给出处理方案 |
| 联系方式 | 平时通过什么渠道报问题，紧急情况用什么渠道 |
| 费用 | 按月还是按年，什么时候付；超出范围的工作怎么计价 |
| 交接 | 不再续约时，交还哪些账号、文档和数据 |

响应时间写「多久回应」和「多久给方案」，不写「多久修好」。有些问题的根因在第三方，修好要多久，你控制不了。

缺陷和新需求的分界最容易起争执。我的划分是：验收清单上验过的功能，现在不按清单那样工作了，算缺陷，在维护里修；验收清单上没有的，算新需求，走变更。验收清单在这里又用上了一次。

费用要看系统规模、响应要求和你要投入的时间，没有通用的数字。有一条底线：维护费要覆盖你每个月实际要花的时间，包括检查备份、看告警、处理小问题，不能只按「出事了才动手」来算。

## 交付以后，留下一份案例

收完尾款，很多人聊天记录一关，项目就结束了。下一个客户问「你以前做过什么」，只能翻出几张零散截图。做过的事很多，能证明的东西很少。

一次真实交付，最值得留下的是：项目为什么开始，需求怎么确认，方案怎么定，怎么交付，哪里踩了坑，最后怎么验收。把它整理成案例。再把报价单、需求清单、验收清单、运维手册和复盘整理成模板，下一个类似的项目就不用从零开始。

案例里的客户信息要脱敏。客户名、金额、服务器地址这些不写，交付时就跟甲方说好。

一笔尾款结算的是这一次项目。案例、流程和信用，负责把下一次机会带回来。

## 这一步交给 AI 做什么

运行说明和运维手册交给 AI 写。它能读完整个仓库，比你凭记忆写得全。

```text
请读完这个仓库的代码、配置文件、部署脚本和 CI 配置，写两份文档。

一、运行说明（给第一次接手的技术人员）
- 需要安装什么，什么版本
- 需要哪些环境变量：只列名字和用途，绝对不要写出任何值
- 从拿到代码到在本机打开页面，每一步的命令
- 怎么初始化示例数据

二、运维手册
- 系统由哪几部分组成，各自部署在哪
- 健康检查地址，正常时返回什么
- 发布新版本和回滚到上一版的步骤
- 日志在哪看
- 备份在哪，怎么恢复
- 从代码和配置里能看出的常见故障点，每条写：现象、先查什么、怎么处理

只写仓库里有依据的内容。仓库里找不到依据的（比如备份放在哪里），
写「待补：」并说明需要谁提供什么信息，不要猜。
```

最后一句最重要。AI 找不到依据时，会编一个看起来合理的答案，比如编一个备份路径。让它标出「待补」，你再去补真实信息。

AI 还能帮你做两件事：把需求确认文件和变更记录整理成验收清单初稿；把你和甲方谈好的条件整理成维护约定。两样你都要逐条核对。

## 你要判断和验收的

- [ ] 交付清单上的每一项都已交出，代码仓库和第三方账号的归属已经说清。
- [ ] 环境变量清单只有名字和用途，值用安全的方式单独交付。
- [ ] 验收清单用业务的话写，包含「不能做」的权限检查。
- [ ] 验收由甲方在线上环境自己操作，全部打勾并签字。
- [ ] 一个没参与开发的人，照运行说明在新电脑上跑起来了。
- [ ] 照运维手册演练过一次回滚和一次备份恢复。
- [ ] 运维手册里没有剩下「待补」。
- [ ] 维护约定写清了包含什么、不包含什么、响应时间分级、费用，以及不续约时怎么交接。
- [ ] 缺陷和新需求的分界以验收清单为准，双方认可。
- [ ] 项目整理成了一份脱敏案例，报价单、验收清单等留成了模板。

## 这一步谁来做

| 交给 AI 的 | 你要判断和验收的 |
|---|---|
| 让 AI 写运行说明和运维手册。 | 甲方能不能自己照着用起来；维护范围写清楚。 |
