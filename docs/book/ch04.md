# 第 4 章　把需求拆成 AI 能做、你能验的任务

## 本章要回答

把客户的一句话变成双方认账的需求；1–2 天的面试题范围怎么取舍；任务拆到多小才合适。

## 示例项目推进到哪

把题目拆成任务清单和先后顺序。

读完这一章，你能做三件事。第一，把客户的一句话，变成一份双方都签字认账的确认清单。第二，时间不够的时候，决定先做什么、做到哪就停、哪些不做。第三，把需求拆成一个个小任务，每个任务交给 AI 做完，你几分钟内就能验收。

拆任务这件事，AI 能帮你，但拍板的是你。拆得好，AI 每次只做一件你看得懂、验得了的事。拆不好，AI 一口气改几十个文件，你只能凭感觉说「好像可以」。

## 一句话不能直接开工

序里讲过我的第一单：老板问什么时候能做完，我回了一句「OK」。需求没问清，演示方式没确认，修改范围没约定。后来那些没问出口的问题一个接一个回来，我只能不停加时间。

AI 让这种问题来得更快。它能把三天的开发压到几个小时。需求没问清楚，几个小时以后，你只是更早拿到一个方向错误的版本。

客户说「帮我做一个平台」。这句话不能直接拿去开发。你要先问：

- 谁来用？
- 最重要的动作是什么？
- 必须有哪些功能？
- 哪些功能这次不做？
- 最后交付什么？
- 谁来验收？
- 交付以后包含几次修改？

很多新手不敢问，怕问得太细显得没经验。于是用一句「好的」结束沟通，回去让 AI 猜。客户以为自己买的是一整套系统，你以为自己只做几个页面。两个人都觉得对方临时加戏。冲突在第一次沟通时就埋下了。

问题问得越早，改起来越便宜。代码写完再确认，一句「这不是我想要的」，就是返工。

## 把问题写成对方能逐条确认的清单

光在聊天里问还不够。聊天记录会被翻过去，口头答应的事会被忘掉。我现在的做法是写一份确认清单，让对方逐条回答，最后签上名字和日期。

陪玩系统交付前，我给甲方写过一份「一次性交付确认问题清单」。它按业务流程排，分成九块：

1. 核心业务流程：有几种下单方式。
2. 用户自己下单：要选哪些信息，必须选打手才能提交吗，提交后是什么状态。
3. 接待代下单：接待要填什么，用户在哪里确认，确认后是否直接付款。
4. 支付确认：用什么支付方式，成功后记录哪些信息，失败了怎么办，已付款的单能不能取消、谁来处理。
5. 打手订单页面：打手能看到哪些单，列表展示哪些信息，要不要点「接单」。
6. 打手交付：开始交付要不要点按钮，交付完提交什么，提交后是否直接完成。
7. 订单状态：列成一张表，每个状态写清怎么触发、代表什么，请甲方确认是否照此执行。
8. 后台处理：后台能看所有订单吗，能改哪些信息，能不能取消、能不能手动标记完成。
9. 验收确认：列出六条验收场景。

开头写了一句话，最后一条又重复了一遍：**本文档未确认的功能，不作为本次交付验收内容。**

这份清单有几个写法，你可以直接照搬：

- **按流程顺序问。** 从下单到交付到后台，跟着一张订单走一遍。对方读着顺，你也不容易漏。
- **问封闭问题。** 「用户是否必须选择打手后才能提交订单？」比「下单流程你想怎么设计？」好回答得多。对方答「是」或「否」，就是一条可以写进代码的规则。
- **给出默认选项。** 下单要填的信息，我先列出服务项目、打手、服务时间、备注，让对方增删。对方改一份草稿，比从零想要轻松。
- **每个问题对应一个代码里的决定。** 「支付成功后，打手是否立即可以看到该订单？」答案直接决定一个状态和一条权限。和代码无关的问题，不放进来。
- **写明没确认的不算。** 这一句划出了交付的边界。以后对方再提新功能，你可以指着清单说：这个不在上次确认的范围里，我们另算。
- **留确认人和日期。** 签了名，这份清单就是双方的约定。

清单不用写得很长，但每一条都要有答案。有一条空着，就是一个以后会回来找你的问题。报价和需求变更怎么处理，放到 [第 12 章](/book/ch12) 讲。

## 1 到 2 天的题，先砍范围

餐厅后台来自一道全栈面试题，时限是 1 到 2 天。题目里有一句话：**范围判断和完整度一样重要。**

题目要的东西很多：一套设计系统和一个专门展示组件的页面；五个后台页面；一个真实的后端点单系统；从数据表一路生成到前端代码的契约链路；前后端测试；运行脚本、种子数据和架构说明。全部做到满分，两天不够。

所以第一件事是砍范围。我把题目要求分成四类：

| 分类 | 放了什么 | 怎么判断 |
| --- | --- | --- |
| 必须做 | 五个页面；创建订单和推进状态；服务端算金额；拒绝不可售的菜和非法的状态跳转；契约生成链路；后端关键流程的测试；种子数据；运行说明 | 题目明确要求，评分标准里点了名 |
| 做到能用就停 | 前端测试只测关键逻辑和状态；手机端只保证能在浏览器里跑 | 题目说手机原生是加分项，前端测试「至少有一些」 |
| 不做 | 登录、在线支付、多门店 | 题目没有要求 |
| 写进取舍说明 | 数据库用托管服务，没有在项目里自带本地数据库；没有做浏览器自动化测试 | 做了取舍，就要说出来 |

最后一类很重要。不做的东西，你自己知道不够，对方不知道。写进说明，对方看到的是一个有判断的人；不写，对方看到的是一个没做完的项目。

接客户的项目也是一样。「必须做」来自对方签过字的确认清单。清单之外的，写进「暂不做」。时间紧的时候，先保证必须做的那一列从头到尾能走通，再去打磨细节。

## 拆到多小才合适

范围定了，下一步是拆成任务。一个任务拆到多小，我用一条标准：**做完以后，你能在几分钟内看到结果，并判断它对不对。**

验收要花半天，任务就太大了。做完什么都看不出来，任务就太碎，或者没意义。

一个大小合适的任务，通常是这样的：

- 一句话能说清做完是什么样子。
- 改动集中在一两个地方。
- 有明确的验收动作：跑一条命令，点一个按钮，看一个数字。
- 能单独提交一次。出了问题，能单独撤回。

餐厅后台从第一个提交到最后一个提交，大约 37 个小时，跨了两个晚上，一共 75 个提交。一个提交基本就是一个任务。把提交记录按时间顺序看，就是一份真实的任务清单：

1. **先写规则。** 第一个提交是题目文档，第二个是给 AI 的工作规则：改动要经过审查，每次改动都要提交。
2. **搭后端空架子，建业务模型。** 菜单、顾客、订单、设置几张表和订单状态规则，在开工后几分钟内就有了。
3. **开放接口，接上契约链路。** 后端接口，接口说明书，前端调用代码依次生成出来。
4. **堵漏洞。** 「拒绝前端传来的价格字段」「把参数校验错误写进接口契约」「给列表接口加条数上限」，每条一个提交。
5. **加种子数据。** 种子数据就是预先写好的演示数据，装上就能看到菜单、顾客和订单。开工后不到一个小时，这一步已经完成。
6. **做页面，配菜品图，中文化。** 第二天上午做首页的图表，把界面文字和业务数据改成中文。
7. **部署和自动检查。** 第二天中午部署上线，晚上加上每次提交自动跑检查。第 7 章会讲，部署为什么应该尽量往前放。
8. **小修小补。** 剩下几十个提交，都是一句话就能说清的小事：时间范围下拉菜单被遮住了、搜索框只在订单页显示、新建订单时可以顺手新建顾客、在顾客页面能改联系方式。

看这份清单，有几个规律：

- 先定规则和数据，再做接口，再做页面，最后打磨。后面的任务都依赖前面的。
- 每个任务的名字就是验收标准。「拒绝前端传来的价格字段」，验收就是带着价格去下单，看它拒不拒。
- 页面的小修放在最后。它们很多，但每个都不影响别的任务。

## 任务之间有先后：画出依赖

小项目的任务，排个先后顺序就够了。任务多了，就要把依赖关系写下来。

依赖，就是「这个任务要等那个任务做完才能开工」。把所有任务和依赖画成一张图，箭头只往前走、不会绕回来，这种图叫有向无环图，常简称 DAG。

陪玩系统第二版有 139 个任务，每个任务都是一个 GitHub issue。issue 正文里固定写两项：属于哪个大块（Parent），依赖哪些任务（Depends on）。我把这些关系整理成一张依赖图，一共 248 条依赖，没有一个循环。没有循环，就说明一定能按顺序做完。

每个大块里的任务，按固定的顺序编号：

| 编号 | 做什么 |
| --- | --- |
| D01 | 定业务规则，由人拍板 |
| DB | 改数据表 |
| API | 写接口 |
| MINI、ADMIN | 做小程序页面、后台页面 |
| MIG | 迁移旧数据 |
| TEST | 端到端测试，整块的收尾 |

当时的进度表里，有两个大块一个任务都没关：一个 16 个子任务，一个 13 个子任务。能开工的入口只剩两个，都是 D01。一个是「固化数量、点单返点、老板归属与禁止代报规则」，一个是「固化个人单价即时生效并待定提现规则」。

挡在前面的，是两条还没拍板的业务规则，跟代码没有关系。规则不定，数据表就没法改，后面的接口和页面都动不了。

所以拆任务时，把「定规则」单独拆成一个任务，排在最前面。这种任务交给人，不交给 AI。

依赖写清以后，还可以给任务打两种标签：前置都做完了的，标「可开工」；还在等别人的，标「被阻塞」。AI 只领可开工的任务。用 issue 管任务的方法，可以看站内的 [GitHub 工作流](/guide/github-workflow)。

你的项目不需要 139 个 issue。几十个任务以内，一个文件里列一张表就够了：任务名、依赖哪几个、状态。

## 一个任务写成什么样

交给 AI 的每个任务，我都写成同一个格式。以「拒绝前端传来的价格字段」为例：

```text
任务：下单接口拒绝前端传来的价格字段
背景：金额必须由服务端按菜品价格和税率计算，前端传来的价格不可信。
要做：下单请求里如果带了单价、小计、税、总价等字段，直接拒绝，返回校验错误，错误里写清是哪个字段。
不做：不改金额计算逻辑；不改前端页面。
依赖：下单接口已完成。
验收：
1. 带着总价字段下单，返回校验错误，错误里写明了这个字段；
2. 不带价格字段下单，订单金额等于各菜单价乘数量之和，再加税；
3. 测试命令全部通过。
完成后：单独提交一次，提交说明写清改了什么。
```

这个格式里，「不做」和「验收」最重要。

「不做」管住 AI 的手。没有这一条，AI 很可能顺手把前端也改了，或者把金额计算重写一遍。改得越多，你要验的就越多。

「验收」写的是你自己要做的动作。写不出验收步骤，说明这个任务还没想清楚，先别交给 AI。

## 交给 AI 的

这一步交给 AI 的，是把每个任务实现出来。拆任务本身，也可以让 AI 先出一版草稿，你来改。

拆任务的时候，可以直接复制这段：

```text
下面是已经和客户确认过的需求清单（附在最后）。请把它拆成任务列表。要求：
- 每个任务做完，我能在 10 分钟内验收；
- 每个任务写清：要做什么、不做什么、依赖哪些任务、验收步骤；
- 需要我拍板的业务规则单独列成任务，排在最前面；
- 之后按数据表、接口、页面、测试、部署的顺序排；
- 清单里没有的功能不要加，单独列在最后的「建议以后做」里；
- 不要写代码。

[需求清单]
```

AI 出的任务列表，你要逐条改：太大的拆开，太碎的合并，验收步骤写不出来的退回去问它。

执行单个任务的时候，每次只交一个：

```text
只做下面这一个任务，不要改任务范围以外的文件。
做完以后：
1. 运行[类型检查和测试命令]，把结果贴给我；
2. 列出改了哪些文件，每个文件改了什么；
3. 照着任务里的验收步骤逐条说明结果；做不到的，直接说做不到。
不要提交，等我验收。

[任务内容]
```

怎么给 AI 定长期规则、怎么审查它的改动，放到 [第 5 章](/book/ch05) 讲。怎么判断一个任务真的做完了，放到 [第 6 章](/book/ch06) 讲。

## 你要判断和验收的

**需求确认**

- [ ] 确认清单按业务流程排，每条都是封闭问题，每条都有答案。
- [ ] 订单状态这类核心规则，列成表格让对方确认过。
- [ ] 写了「未确认的功能不作为本次验收内容」。
- [ ] 有确认人和日期。

**范围**

- [ ] 写清了三栏：必须做、做到能用就停、不做。
- [ ] 不做的和做了取舍的，写进了交付说明。
- [ ] 时间紧的时候，先保证必须做的那一列从头到尾能走通。

**任务大小**

- [ ] 每个任务一句话能说清做完是什么样子。
- [ ] 每个任务写了「不做」和验收步骤。
- [ ] 每个任务的验收，你自己几分钟到十几分钟能做完。
- [ ] 每个任务能单独提交、单独撤回。

**顺序和依赖**

- [ ] 需要人拍板的业务规则，单独成任务，排在最前面。
- [ ] 依赖关系写下来了，没有互相等待的循环。
- [ ] AI 只领前置任务都已完成的任务。

**每个任务交回来以后**

- [ ] 照着验收步骤自己做一遍。不只看 AI 说「完成了」。
- [ ] 看一眼改了哪些文件。范围以外的改动，问清楚为什么，没必要的退回。
- [ ] AI 自己加的、清单里没有的功能，删掉，或者挪到「以后做」。

|---|---|
| 每个任务交给 AI 实现。 | 每个任务做完是什么样子，怎么一眼验收；哪些不做。 |
