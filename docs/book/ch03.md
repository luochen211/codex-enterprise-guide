# 第 3 章　能用现成的就别自己造

## 本章要回答

技术栈怎么选；为什么要尽量用现成的框架、服务和模板。

## 示例项目推进到哪

看懂 餐厅后台每一层用了什么现成方案。

这一章的结论很简单：能用现成的，就用现成的；挑的时候，挑最稳、用的人最多的那一个。

读完这一章，你能给自己的项目一层一层列出该用什么现成方案；能判断 AI 推荐的方案稳不稳；遇到「要不要自己写一个」的时候，能算清这笔账。

## 一种新的浪费

最近我看到一种新的浪费。

有人用 AI 写一个小工具，几百万 token 砸下去，来回修 bug，最后做出一个勉强能跑的半成品。我去 GitHub 上搜了一下，同类项目一大堆。有的已经维护了好几年，几千个 star，文档完整，issue 区有人回复。那个半成品和它们比，差得很远。

他花了那么多时间，图什么？

以前从零写一个功能要三天，你会先查一查有没有现成的。现在一句话丢给 AI，十分钟就出来一个版本，反而没人去查了。AI 降低了写代码的成本，没有降低做错决定的成本。用更快的速度做一件回报很低的事，只是把时间浪费得更彻底。

这种浪费很容易看起来像勤奋。每天都在提交代码，token 在烧，进度条在动。可用户来了吗？有人付钱了吗？核心功能验证了吗？都没有。

我拿自己举个例子。我一直健身，用一个叫训记的 App 记录训练，用了两年多，记了几百条数据。有人问我：你自己会写代码，为什么不自己做一个？

我想了大概十秒。技术上没难度，一个本地数据库、几个页面、一个导出功能，两周能做完。可两周是两百个小时。我手上有商单，有文章要写，有产品要推进。花两周做一个功能不完整的替代品，以后还要一直维护它，处理每次系统升级带来的兼容问题。训记确实有些地方我不喜欢，但这些不爽撑不起两百个小时。

会写，不等于该写。

## 技术栈是一张地图

技术栈，就是一个项目每一层分别用了什么技术。光列出框架名字不够，它要回答下面这几个问题：

| 要回答的问题 | 对应哪一层 |
| --- | --- |
| 用户在哪里看到和操作产品 | 前端、小程序、App |
| 业务规则在哪里执行 | 后端服务 |
| 数据存在哪里 | 数据库、文件存储 |
| 用户怎么登录、怎么区分权限 | 登录和权限 |
| 项目怎么上线 | 托管平台、服务器、自动部署 |
| 出了问题怎么查 | 日志、监控 |

先看每一层要解决什么问题，再比较具体工具。顺序反了，就会在框架名字上争半天，却说不清项目怎么交付。每一层常见的选择，可以看站内的 [技术栈](/guide/tech-stack)。

## 餐厅后台每一层用了什么现成的

下面是餐厅后台每一层用的方案。先说明几个词：

- **ORM**：让你用代码描述数据表、读写数据库的工具，不用手写数据库语句。
- **接口契约**：一份机器能读懂的接口说明书，写清每个接口收什么、返回什么。
- **托管**：别人替你管服务器，你只管把代码交上去。

| 层 | 用的现成方案 | 它替我省掉了什么 |
| --- | --- | --- |
| 项目组织 | pnpm workspace + Turborepo | 前端、后端、共享代码放在一个仓库里，一条命令全部构建和检查 |
| 前端 | Expo + React Native，跑在浏览器里 | 一套代码先在网页上用，以后可以出手机 App |
| 前端取数据 | React Query | 加载中、缓存、刷新、出错重试，不用自己写 |
| 后端 | Hono，跑在 Cloudflare Workers 上 | 不用自己装服务器，一条命令部署 |
| 数据库 | PostgreSQL，用 Neon 托管 | 不用自己装数据库、管备份 |
| 数据表定义 | Drizzle ORM + drizzle-zod | 用代码写表结构，自动得到对应的校验规则 |
| 接口契约和前端调用代码 | OpenAPI 生成 + Orval | 接口说明书自动生成，前端调用代码和类型也自动生成 |
| 前端上线 | Vercel | 代码推到 GitHub 就自动部署 |
| 自动检查 | GitHub Actions | 每次提交自动跑类型检查、测试和构建 |
| 菜品图片 | AI 生成的 11 张图 | 不用找人拍照 |

这张表里，几乎每一层都是现成的。我自己写的部分，是只有这家餐厅才有的东西：订单怎么流转，金额怎么算，哪些菜能卖，页面怎么组合。

这就是分工的边界。通用的事交给现成方案。只属于你这个业务的规则，才值得自己写，也才值得你花时间去验收。

契约这一层值得多说两句。餐厅后台的数据只在一个地方定义：数据表。从数据表自动生成校验规则，再生成接口说明书，再生成前端调用代码。四样东西，只有第一样是写出来的，后面三样都是生成的。

这样做对用 AI 编程特别有用。你让 AI 给订单加一个字段，它只改数据表，重新生成一次，前后端就都对上了。要是这四样都靠手写，AI 很可能改了三处、漏了一处，页面上的字段和后端对不上，你还很难发现。

现成方案也有代价，要写下来。餐厅后台的数据库选了 Neon 这种托管的 PostgreSQL，没有在项目里自带一个本地数据库。好处是部署省事，代价是本地开发也要联网连数据库。前端测试只测了关键逻辑和状态，没有做浏览器自动化。这两条我都写进了项目说明的「取舍」一节。

## 同一个问题，两套答案都对

陪玩系统用的是另一套：Next.js 15、TypeScript、Tailwind CSS、Prisma、PostgreSQL、Redis。

有意思的是，餐厅后台那道题明确规定，不许把指定的技术换成 Next.js、NestJS、Prisma、tRPC、Supabase、Firebase 这些替代品。陪玩系统用的 Next.js 和 Prisma，正好在禁用名单里。

两套都能做出能用的系统。陪玩系统已经交付给客户在用，餐厅后台也部署上线了。那道题禁用别的技术，原因是出题公司自己用那一套，它要看你能不能在团队已有的技术上干活。

所以「哪个框架最好」没有答案。主流框架都能用。要比的是这几件事：

1. **对方已经在用什么。** 接手别人的项目，或者进别人的团队，就用别人的那一套。你换一套自己喜欢的，后面没人能接手。
2. **你和 AI 熟不熟。** 用得越多的技术，AI 见过的代码越多，写出来越少出错。
3. **最后部署在哪里。** 用户主要在国内还是海外，要不要自己的服务器，决定了托管平台能不能用。海外托管平台在国内访问快不快，要先测一下。

两个项目都选了 PostgreSQL。数据库这一层，选最常见的那个，基本不会错。

## 我判断要不要自己写的三个问题

遇到「要不要自己写一个」，我会问自己三个问题：

1. **有没有现成的？** GitHub 上搜过了吗？质量怎么样？还有没有人在维护？
2. **接进来要多少成本？** 用现成的，需要改多少代码，看多少文档？
3. **这个不爽值多少钱？** 自己从零写要多少时间？这些时间拿去做别的，会不会更划算？

问完这三个，大部分时候答案都是用现成的。

最该用现成的，是登录和支付。很多人产品还没验证、用户还没来，先写登录，再接支付，再补权限。一个月过去，基础设施终于跑起来了。产品卖给谁，用户为什么付钱，第一批用户从哪来，还是空的。

登录和支付早就有成熟的服务。它们还牵扯安全和资金，自己写出错的代价很高。你要做的是挑一个适合你业务的接进来，然后尽快把产品推到用户面前。陪玩系统里，顾客的充值、退款这类真实交易，也交给了专门的支付服务方处理，系统这边只做页面和入口。

少造轮子，不代表能力变弱。现成的框架、云服务、支付和登录服务都是杠杆，会搜索也是杠杆。判断哪些值得自己造、哪些直接用，这个判断目前还得你自己来做。

## 挑哪一个：稳、常见、AI 熟

AI 会给你推荐好几个方案。挑的时候，照这张表一项项看：

| 看什么 | 怎么看 |
| --- | --- |
| 用的人多不多 | GitHub star 数、下载量；遇到问题能不能搜到答案 |
| 还有没有人维护 | 最近一次发版是什么时候；issue 有没有人回 |
| 文档全不全 | 有没有官方的快速上手指南，照着能不能跑通 |
| 接入要多少成本 | 要改多少代码，要学多少概念 |
| 长期要花多少钱 | 怎么收费；用户多了以后每月多少钱 |
| 以后能不能换掉 | 数据能不能导出；换一家要改多少 |
| AI 熟不熟 | 让 AI 写一个最小例子，看它会不会编出不存在的用法 |
| 和现有项目一不一致 | 客户或团队已经在用的，优先 |

新出的框架要特别小心。它可能确实更好，但 AI 不一定认识它最新的写法，经常编出不存在的接口。你又不一定看得出来。用 AI 编程，选老一点、常见一点的技术，出错少很多。

不要为了新鲜感换技术。项目做到一半换框架，前面验收过的东西要重新验一遍。

## 交给 AI 的

这一步交给 AI 的，是列出候选方案和取舍。你来拍板。

可以直接复制下面这段，把方括号里的内容换成你自己的情况：

```text
我要做一个[餐厅运营后台]。形态：[管理后台，浏览器里使用，以后可能出手机端]。
需要：后端接口、数据库、前端页面、登录、上线部署。
我的情况：[会一点 TypeScript；只有我一个人；预算很低；用户主要在国内]。

请按「前端、后端、数据库、登录、支付、部署、监控」逐层列出候选方案，每层 2 到 3 个。每个方案写清：
- 它替我省掉哪些工作；
- 用的人多不多，还有没有活跃维护；
- 怎么收费，用户多了以后大概每月多少钱；
- 以后要换掉它，难度有多大。

最后每层推荐一个最稳、最常见的方案，说明为什么不选其他的。
不要推荐发布不到一年的框架。
不要写代码。
```

开始做某个功能之前，再加一道检查：

```text
在动手写[导出 Excel / 图片上传 / 发送短信]之前，先列出能直接用的现成库或服务，
写清每个的维护情况、接入步骤和限制。
如果有合适的现成方案，用它，不要自己从零写。
```

AI 给的维护情况和 star 数，可能是旧的，也可能是编的。挑出来的方案，你要自己去 GitHub 和官网看一眼。

## 你要判断和验收的

- [ ] 每一层都写清了：用什么，替你省了什么，怎么验证它能用。
- [ ] 自己写的部分只剩业务规则。通用功能（登录、支付、文件存储、发邮件短信）都用了现成方案。
- [ ] 每个选中的方案，你亲自看过它的 GitHub 或官网：最近一年有更新，文档能照着跑通。
- [ ] 如果是接手别人的项目，沿用对方的技术，没有换成你更喜欢的那一套。
- [ ] 没有选发布不到一年、用的人很少的新框架。
- [ ] 托管和第三方服务的收费方式你看过，知道用户多了以后大概要花多少钱。
- [ ] 取舍写进了项目说明：选了什么，放弃了什么，代价是什么。
- [ ] 能用几行字把技术栈讲给 AI 听：每一层用什么、怎么启动、怎么构建、怎么测试、部署到哪。

最后一条，是给下一章准备的。技术栈说得清，下一章拆任务的时候，AI 才知道每个任务该去改哪一层、跑什么命令。

## 这一步谁来做

| 交给 AI 的 | 你要判断和验收的 |
|---|---|
| 让 AI 列出候选方案和取舍。 | 选最稳、最常见的；不为了新奇换技术。 |
