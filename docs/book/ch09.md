# 第 9 章　收钱：支付、退款与对账

## 本章要回答

接微信、支付宝；金额为什么只能在服务端算；回调丢了、重复了怎么办；每天的钱怎么对得上。

## 示例项目推进到哪

接入在线付款、退款和每日对账。

读完这一章，你能判断一条收钱链路哪里会出错，能让 AI 按支付平台的文档把付款、退款接进来，并且每天对一次账，确认系统里的钱和平台里的钱对得上。

先把结论放在前面。接支付有五条规矩：

1. 金额只在服务端算，前端传来的价格一概不信。
2. 订单付没付钱，以支付平台的通知和查询结果为准，不以前端的「支付成功」页面为准。
3. 每一笔付款、每一笔退款，都有自己的单号和状态记录。
4. 同一个通知收到两次、同一个按钮点了两次，结果和只发生一次一样。
5. 每天和平台的账单对一次账，对不上的单子有人处理。

餐厅后台在这一章接上在线付款、退款和每日对账。

## 钱是怎么走的

一笔在线付款，从顾客点下「支付」到钱进商户账户，大致经过这几步：

1. 顾客选好菜，提交订单。
2. 服务端按数据库里的价格算出金额，建好订单。
3. 服务端拿着订单号和金额，去支付平台「下单」。平台返回拉起支付需要的参数。
4. 前端用这些参数拉起微信或支付宝的付款界面，顾客输密码付款。
5. 支付平台把付款结果发给你的服务端。这一步叫回调，也叫支付结果通知：平台主动访问你事先给它的一个地址，告诉你「这一单付了」。
6. 服务端核对通知内容，把订单标记为已支付。
7. 第二天，下载平台的账单，和自己的记录对一遍。

第 4 步结束时，前端会显示「支付成功」。这个页面只说明顾客那边的操作走完了，不能当作收到钱的证据：页面可以被伪造，网络也可能在半路断掉。订单状态只能由第 5、6 步改。

## 动手之前要准备什么

**商户号。** 接微信支付要有微信支付商户号，接支付宝要有支付宝的商家账号。两者都要用企业或个体工商户的营业执照申请。如果你是给甲方做系统，商户号要用甲方的主体申请，钱直接进甲方的账户。你只拿到接入需要的配置，不要让钱经过你自己的账户。

**密钥。** 接入时会拿到商户的 API 密钥、证书和私钥。它们能用来发起退款，和银行卡密码一个级别。按第 7 章的做法放进环境变量或平台的密钥管理里，不进代码仓库，也不贴进和 AI 的对话里。

**应用和商户号的绑定。** 小程序、公众号或 App 要和商户号关联起来，才能在里面拉起支付。这一步在商户平台后台操作，需要甲方的管理员账号配合，要提前排进计划。

**选对支付场景。** 同样是微信支付，按顾客在哪里付钱分成好几种接法：小程序里付款、扫二维码付款、手机浏览器里付款、App 里付款。每种场景的下单接口不一样，返回的东西也不一样。

陪玩系统在这里踩过坑。小程序里的微信支付要调 JSAPI 下单接口，平台返回一个 `prepay_id`，小程序用它拉起付款。扫码支付要调 Native 下单接口，返回的是一个 `code_url`，用来生成二维码。当时有人把 Native 的下单地址复用成了小程序的下单地址。接口能调通，也返回了结果，但返回的是 `code_url`，小程序拿它拉不起支付。后来我们在说明文档里专门写了一条：小程序必须用 JSAPI 下单地址，不要复用 Native 的。

放到餐厅后台：前台收银时在屏幕上展示一个二维码让顾客扫，用 Native；顾客在小程序里自己点单付款，用 JSAPI。让 AI 接入时，要把场景说清楚，并要求它先读对应场景的官方文档。

**写清支付由谁负责。** 陪玩系统的支付最后交给了一家外部公司做。我在仓库的审查文档里写明了边界：商户参数、支付回调、真实扣款、对账和支付服务的可用性，不在本仓库的验收范围里；本仓库只负责支付、充值相关页面和对接入口存在。这样写很有必要。钱出了问题，大家第一个会看写系统的人。边界没有写下来，你很难说清楚这不是你的责任。

**不要替别人收钱再分钱。** 如果你的系统先把顾客的钱收进平台自己的账户，再分给各家店铺或各个服务者，这就涉及资金的二次清算，没有支付牌照的公司不能这么做。陪玩平台、多商户商城都会碰到这个问题。遇到这种业务，先去问支付平台的客户经理有没有分账功能，再请律师看一下资金流。不要让 AI 自己设计一套「平台代收、定期打款」的方案。

## 金额只能在服务端算

餐厅后台的下单逻辑，是这道面试题里我最看重的一段。前端只传两样东西：顾客是谁，点了哪些菜、各几份。价格一个字都不传。服务端拿到请求后：

- 检查至少点了一道菜，同一道菜没有重复出现，数量都是正整数。
- 检查餐厅现在接不接单，顾客是否存在。
- 从数据库按菜品编号读出菜品，找不到的、停售的直接拒绝。
- 用数据库里的单价乘数量，算出每一行的金额，加起来是小计，再按设置里的税率算税，得到总价。
- 把菜名和单价一起抄进订单明细里。

最后一条容易被忽略。菜单价格以后会改，订单明细里存的是下单那一刻的价格。下个月菜价涨了，上个月的订单金额不会跟着变，对账才对得上。

所有金额都存成整数，单位是分。一份 14 元的菜存成 1400。原因是计算机里的小数有精度问题，最有名的例子是 0.1 加 0.2 不等于 0.3。钱的计算一旦用小数，就会出现一分钱对不上的情况，而且很难查。

接了支付以后，再加三条：

- 向支付平台下单时，金额从数据库里这笔订单的总价读，不从请求里读。
- 微信支付的金额单位是分，用整数；支付宝的金额单位是元，带两位小数。转换只写在一个函数里，并且要有测试。
- 收到回调时，核对通知里的金额和订单总价是否一致。不一致就不改状态，记下来报警。

## 回调丢了、重复了怎么办

回调是平台主动发给你的，你控制不了它什么时候来、来几次。会遇到四种情况：

| 情况 | 原因 | 怎么处理 |
|---|---|---|
| 来晚了 | 平台或网络延迟 | 订单先显示「支付确认中」，不要急着判失败 |
| 来了好几次 | 你没有按要求回复成功，平台会隔一段时间重发 | 处理要幂等：已经是已支付的订单，直接回复成功 |
| 一直没来 | 你的服务器当时挂了，或者回调地址配错了 | 定时任务主动去平台查询订单状态 |
| 有人伪造 | 有人知道你的回调地址，自己发一个「已支付」 | 验签，并核对金额和商户号 |

几个词解释一下。**验签**：平台发通知时会用自己的私钥签名，你用平台的公钥或证书验证签名，验得过才说明这条通知确实来自平台、内容没被改过。微信支付新版接口的通知内容还是加密的，要用你的密钥解密后才能读。**幂等**：同一个操作做一次和做很多次，结果一样。

处理一条支付通知的顺序是：

1. 验签，必要时解密。验不过直接拒绝。
2. 按商户订单号找到订单。找不到就记录下来，留给对账处理。
3. 核对金额、商户号、应用编号，都是自己的才继续。
4. 用带条件的更新改状态：只有「待支付」的订单才能改成「已支付」。这和第 8 章防卖超用的是同一个办法，两条通知同时到，也只有一条能改成功。
5. 改完、写进数据库以后，再按文档要求的格式回复平台「成功」。顺序反过来，回复了成功但没存进去，平台不会再发，这笔钱就成了系统里没有的钱。

再加两个定时任务：

- **补查**：每隔几分钟，找出下单超过一定时间、还是「待支付」的订单，调平台的查询接口，按查询结果更新状态。
- **关单**：超过付款时限还没付的订单，系统里标为已关闭，同时调平台的关单接口。只在自己系统里关，不通知平台，顾客过一会儿可能还能付上，钱进来了订单却已经取消。

下单本身也要防重复。陪玩系统的支付下单请求里有一个 `idempotencyKey` 字段，也就是幂等键。它的用法是：前端为每一次下单生成一个编号，顾客网络卡顿连点了两次，两次请求带的编号相同，服务端只建一个订单，第二次直接返回第一次的结果。

为了把这些事做清楚，我会给支付单独建一张记录表，不把支付信息直接塞进订单表。每条记录有：商户订单号、平台交易号、金额、状态、创建时间、支付时间、最后一次收到通知的时间。支付状态大致是这样走的：

```text
待支付 ──付款成功──> 已支付 ──发起退款──> 退款中 ──> 部分退款 / 全额退款
   └──超时未付──> 已关闭
```

订单状态还是原来那套：待接单、已接单、制作中、待取餐、已完成、已取消。两套状态分开存，各管各的。订单从哪个状态能走到哪个状态，第 2 章已经定过，这里只是在它旁边多了一条钱的线。

## 退款

餐厅后台的订单在完成之前都可以取消。如果顾客已经付了钱，取消就要退款。还有一种情况是部分退款：一单点了三道菜，有一道做不出来，只退这一道的钱。

退款要注意这几件事：

- **每笔退款有自己的退款单号。** 由你的系统生成。同一个退款单号重复提交，平台只会退一次。所以重试时要用原来的退款单号，不要重新生成。
- **退款不是马上完成的。** 提交后先是「退款中」，结果通过退款通知或查询接口拿到。处理方式和支付回调一样：验签、核对、幂等。
- **退款总额不能超过实付金额。** 多次部分退款时，服务端要把已退的金额加起来校验。
- **谁能退款要受控。** 退款是直接往外出钱的操作。在餐厅后台里，只有店长以上的角色能发起，必须填原因，并且写进操作记录。第 10 章会讲角色和操作记录。
- **退款失败要有人管。** 退款可能因为各种原因失败。失败的单子进入一个待处理列表，并通知负责人，不要让它停在「退款中」没人看。

陪玩系统还有一种动钱的操作：管理员在后台手动调整用户余额。这类内部账务动作不走支付平台，更要有权限控制和记录，我们在审查时把它单独列出来，按内部账务权限另行验收。

## 每天对一次账

回调会丢，代码会有错，有人会在后台手动操作。对账是最后一道网。

微信支付和支付宝都提供按天下载的交易账单，里面有前一天每一笔交易和退款的明细，包括手续费。对账的做法是：

1. 每天定时下载前一天的账单。
2. 按商户订单号，把账单里的每一笔和自己的支付记录、退款记录逐条对。
3. 再对总数：交易笔数、交易总额、退款总额、手续费。
4. 对不上的生成一张差异清单，发给负责人。

差异一般分这几类：

| 差异 | 可能的原因 | 怎么处理 |
|---|---|---|
| 平台有，系统没有 | 回调丢了，补查也没补上 | 核实后补记到订单上，或者联系顾客退款 |
| 系统有，平台没有 | 有人伪造回调成功了，或者代码把没付的单标成了已付 | 最严重的一类，马上查，先暂停相关操作 |
| 金额或状态不一致 | 部分退款没同步，或者金额换算错了 | 逐笔查，修正后记下原因 |
| 跨天 | 23:59 付款，通知在第二天才处理 | 标为待定，第二天的账单里再对一次 |

对账程序只负责找出差异，不要让它自动改钱。每一处修正都要有人确认，并且留下记录。

账单里的手续费也要留意。支付平台会从每笔交易里扣一部分手续费，商户实际到账的钱比交易额少。经营看板上显示的营收是交易额还是到账金额，要和老板说清楚，第 11 章会讲。

## 用真钱小额走一遍

支付接完以后，一定要在生产环境用真钱走一遍。测试环境里一切正常，不代表生产配置是对的：商户号、证书、回调地址、域名，任何一个配错，都只有在生产上才会暴露出来。

做法是建一道价格很低的测试菜品，只对你自己可见，然后走完这一遍：

1. 下单、付款，看订单变成「已支付」。
2. 去数据库或后台看支付记录，金额、平台交易号都在。
3. 对这一单发起全额退款，看状态变成「退款中」再变成「已退款」，确认钱回到了付款账户。
4. 再下一单，付款后立刻关掉页面，确认订单状态照样会变成已支付。
5. 第二天，确认对账程序跑了，这两笔都出现在账单里并且对上了。

在预发环境，还要故意让回调接口返回一次失败，确认平台重发以后系统只记了一次账。

测完把测试菜品下架。之后每次改动支付相关的代码，都重新走一遍第 1 到第 3 步。

## 交给 AI 的

可以把下面这段直接发给 AI：

```text
给餐厅后台接入微信支付（APIv3）。场景有两个：
- 前台收银：Native 下单，展示二维码给顾客扫；
- 顾客小程序点单：JSAPI 下单，用 prepay_id 拉起支付。注意不要把 Native 的下单地址用在小程序上。

开始写代码之前，先读这两个场景的官方文档，列出要用到的接口、字段和金额单位，给我确认。

要求：
1. 新建支付记录表和退款记录表，状态分开管理，不改原有的订单状态机。
2. 下单金额只从数据库里订单的总价读取，单位是分。
3. 回调处理顺序：验签并解密 → 按商户订单号找订单 → 核对金额和商户号 → 用“只有待支付才能改为已支付”的条件更新 → 写库成功后再回复成功。
4. 加两个定时任务：补查超时未确认的订单；关闭超时未付的订单并调用平台关单接口。
5. 退款使用系统生成的退款单号，重试复用原单号；校验累计退款不超过实付金额。
6. 每日对账：下载前一天的交易账单，逐笔比对，输出差异清单并发到飞书群。对账程序不自动修改任何金额。
7. 商户号、密钥、证书全部从环境变量读，不写进代码和测试数据。
8. 测试覆盖：重复回调只记一次账、金额不符不改状态、验签失败拒绝、累计退款超额被拒绝。
```

如果接的是支付宝，把场景和接口名换掉，并提醒 AI 支付宝的金额单位是元。

## 你要判断和验收的

| 检查项 | 怎么验 |
|---|---|
| 金额只在服务端算 | 在下单请求里手动加一个价格字段，或者改掉菜品信息里的价格，服务端算出的总价不变 |
| 商户号属于甲方 | 在商户平台确认主体名称，钱进的是甲方账户 |
| 密钥没进仓库 | 在仓库里搜索商户号和密钥片段，搜不到 |
| 真钱走通付款和退款 | 按上一节五步走完，钱确实回到了付款账户 |
| 重复回调不重复记账 | 测试通过，并在预发上手动重放一次通知 |
| 伪造回调无效 | 不带签名或者签名错误的请求被拒绝 |
| 关单生效 | 超时订单在系统和平台两边都关闭了 |
| 退款受控 | 用没有退款权限的账号调退款接口，被拒绝；退款有操作记录 |
| 每日对账在跑 | 连续几天收到对账结果；人为制造一笔差异，能被发现 |
| 边界写清楚 | 如果支付由别人负责，文档里写明了哪些不归你验收 |

最后一条要自己守住：对账出现差异的那天，当天就查。差异放着不管，过几天就没人记得那天发生了什么。测试怎么优先覆盖会出钱的地方，见 [第 6 章](/book/ch06)。
