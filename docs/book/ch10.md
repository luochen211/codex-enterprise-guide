## 本章要回答

面试题没做登录和角色，商用必须补；谁能看什么、改什么；个人信息怎么存；备案、隐私政策、平台审核。

## 示例项目推进到哪

补上登录与角色、操作记录和隐私政策。

读完这一章，你能给餐厅后台列出一张权限表，说清谁能看什么、改什么；能自己动手测出越权漏洞；知道顾客的个人信息该怎么存；知道上线前在合规上要办哪些事、去问谁。

餐厅后台这道面试题没有做登录。任何人打开网址，就能改菜价、改税率、看所有顾客的手机号。一两天的面试题这样做没问题，题目考的是业务逻辑。要拿去给真实的餐厅用，这一章的三样东西必须补上：登录和角色、操作记录、隐私政策。

先说明一点：我不是律师。这一章讲合规的部分，只讲做系统的人需要知道的要点和该去问谁。具体到某个项目要办什么，以主管部门、平台和律师的答复为准。

## 两个词：认证和授权

- **认证**：确认你是谁。登录就是认证。
- **授权**：确认你能做什么。店长能退款、服务员不能，这是授权。

两件事失败时，返回的结果不一样。没登录或者登录过期，返回 401，前端跳到登录页。登录了但没有权限，返回 403，前端提示「没有权限」。

餐厅后台原来已经有一套统一的业务错误：每种错误有一个固定的错误码，比如「菜品不存在」「订单状态不能这样改」，再配一个 HTTP 状态码。补权限时，在这套错误里加上「未登录」和「无权限」两种就行，不用另起一套。

## 先画一张权限表

写代码之前，先和老板一起把角色和权限定下来。餐厅后台可以分四个角色：

| 功能 | 老板 | 店长 | 前台 | 后厨 |
|---|---|---|---|---|
| 看经营首页的营收数据 | ✓ | ✓ | ✗ | ✗ |
| 创建订单 | ✓ | ✓ | ✓ | ✗ |
| 接单、推进订单状态 | ✓ | ✓ | ✓ | 只能把「制作中」改成「待取餐」 |
| 取消订单 | ✓ | ✓ | 只能取消未接的单 | ✗ |
| 退款 | ✓ | ✓ | ✗ | ✗ |
| 停售、恢复菜品 | ✓ | ✓ | ✓ | ✓ |
| 修改菜品价格 | ✓ | ✓ | ✗ | ✗ |
| 看顾客完整手机号 | ✓ | ✓ | 只看后四位 | ✗ |
| 导出顾客名单 | ✓ | ✗ | ✗ | ✗ |
| 修改税率、营业状态等设置 | ✓ | ✓ | ✗ | ✗ |
| 管理员工账号 | ✓ | ✗ | ✗ | ✗ |
| 看操作记录 | ✓ | ✗ | ✗ | ✗ |

这张表要老板签字认可。表里每一个勾，以后都对应一条测试。

如果系统以后要卖给多家餐厅用，还要加一层范围：A 店的店长只能看 A 店的数据。陪玩系统有多个俱乐部，管理员的订单列表、详情、审核，全部复用同一个「俱乐部范围」的判断函数，不在每个页面各写一遍。各写一遍，迟早有一处会漏。

## 权限要在服务端判断

陪玩系统的超级管理员后台，我做过一次对齐审查，权限部分的问题很典型。

一开始，超管后台用的是 Basic Auth 保护：打开页面时浏览器弹出一个用户名密码框，输对了才能进。生产环境启动时会强制检查有没有配置这个密码。它能挡住路人，但是缺的东西很多：没有登录页和退出，输错多少次都不会被锁，登录没有记录，也没有二次验证。

更大的问题在后面。角色表里能存「哪个角色能操作哪个模块、哪些动作、在什么范围」，但业务代码执行时，并没有普遍去查这张表。审查结论里有一条列为最高优先级：所有涉及资金和权限的服务端操作，要统一取当前用户、统一判断权限，不能因为某人打开了这个页面，就当他是超级管理员。

页面藏起来了，接口还在。按钮不显示，有人照样可以用浏览器的开发者工具，或者一条命令，直接调接口。陪玩系统后来写审核规格时专门写了一句：前端按钮不作为授权依据。

还有一个过渡期的做法值得说。陪玩系统早期为了让小程序尽快联调，服务端除了认登录后发的会话凭证，也接受请求头里直接带用户编号或微信 OpenID 来识别用户。联调阶段这很方便。到了生产环境，请求头里的东西谁都能填，填别人的编号就能冒充别人。生产上只能认服务端自己发出去的会话凭证。

所以餐厅后台的每一个接口，都按同一个顺序检查：

1. 你是谁：从会话凭证里取出当前用户，取不到就 401。
2. 账号还能用吗：被停用的账号，旧的会话也立刻失效。
3. 你的角色能不能做这个动作：不能就 403。
4. 你操作的数据在不在你的范围里：别的店的订单，当作不存在。
5. 这个动作在当前状态下合不合规则：比如已完成的订单不能退款。

登录本身也有几条底线：

- 密码只存加密后的结果，用专门为密码设计的慢速哈希算法，任何人都看不到原密码。
- 连续输错几次就暂时锁定，或者要求输入验证码。
- 会话有过期时间，退出登录后凭证作废。
- 员工离职当天停用账号。陪玩系统的账号管理有启用和停用，就是为了这个。
- 不共用账号。一个账号几个人用，操作记录就失去了意义。

## 流程本身也是权限

权限要看「谁」，也要看「在什么状态下」。

陪玩系统的提现审核有这样一条流程：陪玩师申请提现，管理员审核；金额大的或有风险的，转给更高一级复核；通过后才能放款。审查时发现了一个漏洞：转复核的申请，可以跳过复核，直接确认放款。另外，已经通过、甚至已经放款的申请，在系统再次同步收入时，可能被新的收入覆盖掉。

修复后的规则是：

- 普通审核只能处理「待审核」和「挂起」的申请；复核只能处理「转复核」的申请；放款只能处理「已通过」的申请。
- 每个动作都用「状态加更新时间」作为条件去更新，两个人同时操作，只有一个能成功。
- 状态变更、关联收益、操作记录在同一个事务里写入，要么都成功，要么都不算。
- 已经结束的申请不再被同步复用，之后的新收入生成新的申请。
- 超管网页和管理员小程序两个入口共用同一套状态检查，不能从另一个入口绕过去。

最后一条很容易漏。同一个动作有两个入口，AI 往往会在每个入口各写一份检查，改了一处忘了另一处，漏洞就出在没改的那一处。

放到餐厅后台：退款只能对已支付的订单发起；取消要符合订单状态机；已完成的订单不能再改金额。这些规则和角色一起，都写在服务端。

## 操作记录

操作记录也叫审计日志，就是「谁、在什么时候、对什么、做了什么」的流水账。出了事，它是唯一能说清楚责任的东西。

每条记录至少有这些内容：操作人、时间、动作、操作对象、改之前的值、改之后的值、原因、来源（比如 IP 地址或设备）。

不是所有操作都要记。先记这几类：

- 动钱的：退款、手动改金额、手动调余额。
- 动权限的：新建账号、改角色、停用账号。
- 动关键配置的：改菜价、改税率、关闭接单。
- 动个人信息的：查看完整手机号、导出顾客名单。

陪玩系统的审计日志有列表、搜索和详情，审查时还是发现了几个缺口：不能按时间筛选，没有可用的导出，没有按结构记下改之前和改之后的值，也没有保留期限和防篡改的规定。这几样在餐厅后台一开始就做上：

- 操作记录和业务修改在同一个事务里写，不会出现改了却没记的情况。
- 记录只能新增，系统里没有修改和删除操作记录的功能。
- 前后值按字段结构存，方便以后查「这道菜的价格被谁改过」。
- 保留多久，要看业务需要和法规要求。网络安全方面的法规对日志留存有要求，具体留多久、哪些日志算在内，问客户的法务或律师。

## 个人信息怎么存

个人信息就是能单独或者和其他信息结合起来认出某个人的信息。餐厅后台的顾客表里有姓名、手机号、邮箱，再加上每个人的订单记录，都属于个人信息。

《个人信息保护法》对做系统的人，最重要的要求可以归成几条：

- **告知并取得同意。** 收集之前告诉用户收什么、为什么收、怎么用，用户同意了才收。
- **最少必要。** 只收业务需要的。点餐需要手机号联系取餐，不需要身份证号和生日。
- **敏感个人信息要单独同意。** 法律列出的敏感个人信息包括生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹，以及不满十四周岁未成年人的个人信息。处理这类信息要求更严。餐厅后台用不到，就一样都不要收。
- **用户有权查看、更正和删除自己的信息。** 用户要求删除时，你要有办法删干净。
- **要有安全措施，出了泄露要能处置。**

落到系统上，就是下面这张清单：

| 做法 | 说明 |
|---|---|
| 列表里脱敏 | 手机号在列表里显示成 138****5678。陪玩系统审查时就把账号列表的手机号改成了脱敏显示 |
| 密码不显示 | 陪玩系统给管理员设初始密码的输入框，原来是明文显示，后来改成隐藏输入 |
| 敏感字段加密存储 | 如果确实要存身份证号这类信息，数据库里存加密后的值 |
| 日志里不打印 | 日志里不出现密码、会话凭证、完整手机号 |
| 生产数据不出生产 | 不把真实顾客数据拷到自己电脑上调试，不贴进和 AI 的对话里。调试用造出来的测试数据 |
| 备份同样保护 | 备份里有全部个人信息，加密后再存出去，见第 8 章 |
| 导出要权限、要记录 | 只有老板能导出，每次导出都写进操作记录 |
| 第三方要列清楚 | 支付、短信、地图、统计这些第三方服务会拿到哪些数据，写进隐私政策 |
| 能删 | 顾客要求删除时，删除或匿名化他的个人信息；订单金额这类经营数据按规定保留的，要和个人身份断开 |

## 上线前要办的事和该问谁

这部分最容易被开发者忽略，因为它们不在代码里。但它们会直接决定系统能不能上线、上线后会不会被下架。下面是常见的几项：

| 事项 | 什么时候需要 | 去问谁、在哪办 |
|---|---|---|
| ICP 备案 | 网站放在中国大陆的服务器上，用自己的域名对外访问 | 通过云服务商的备案系统提交，主体一般是甲方。要等审核，排进上线计划 |
| 经营性许可证 | 网站本身通过互联网提供收费的信息服务 | 先问云服务商的备案客服，再问当地通信管理部门 |
| 公安联网备案 | 网站开通以后 | 全国互联网安全管理服务平台，按当地要求办 |
| 小程序、App 备案 | 小程序和 App 上架之前 | 在小程序后台或应用商店按指引提交 |
| 平台审核 | 小程序每次发布、App 每次上架 | 平台后台。要选对服务类目，有的类目要上传资质证明；小程序还要在后台填写用户隐私保护指引 |
| 隐私政策 | 收集任何个人信息之前 | 你起草，甲方确认，涉及敏感信息或业务复杂时请律师看 |
| 等级保护 | 客户是政府、学校、医院、金融机构等时常被要求 | 先问客户要求什么级别，再找有资质的测评机构 |
| 支付 | 接入在线支付 | 商户号用甲方主体；涉及替别人收款再分钱时，问支付平台和律师，见第 9 章 |

这些事大部分要用甲方的主体去办，要甲方提供营业执照、负责人信息，要等审核。它们会占用时间，有的审核要等上一段时间。所以接项目时就要把它们列出来，写进排期和报价，并在合同里写清楚谁负责办、谁承担费用。报价和排期见 [第 12 章](/book/ch12)。

隐私政策可以交给 AI 写初稿，但写的依据必须是系统实际收集的字段，不能套一份网上的模板。模板里写「我们不收集位置信息」，你的系统却调了定位接口，这份政策反而成了证据。每次加了新的个人信息字段或者新接了第三方服务，都要回头改隐私政策。

## 交给 AI 的

```text
给餐厅后台补上登录、角色和操作记录。权限表如下（贴上你和老板确认过的权限表）。

要求：
1. 登录：账号密码登录，密码用 argon2 或 bcrypt 存储；连续输错 5 次锁定 15 分钟；
   会话有过期时间，退出后失效；被停用账号的会话立即失效。
2. 鉴权：写一个统一的鉴权中间件，每个接口按顺序检查：
   取当前用户（失败 401）→ 账号状态 → 角色权限（失败 403）→ 数据范围 → 业务状态规则。
   不允许在单个接口里各写各的判断。错误码加进现有的统一业务错误里。
3. 前端按角色隐藏按钮只是为了体验，所有判断以服务端为准。
4. 操作记录：退款、改价、改设置、改角色、停用账号、查看完整手机号、导出顾客，
   都写操作记录，字段包括操作人、时间、动作、对象、改前值、改后值、原因、来源 IP。
   与业务修改在同一个事务里写入。系统不提供修改和删除操作记录的接口。
5. 顾客手机号：列表脱敏，按权限查看完整号码。日志中不得输出密码、会话凭证、完整手机号。
6. 测试：按权限表为每个角色、每个动作写测试，包括“没权限被拒绝”的反向用例。
7. 列出系统目前收集的所有个人信息字段和接入的第三方服务，作为起草隐私政策的依据。
```

## 你要判断和验收的

越权要自己动手测，不能只看 AI 写的测试是否通过。准备四个角色各一个账号，再加一个已停用的账号，按下表逐条试：

| 测试 | 预期 |
|---|---|
| 不登录，直接调订单列表接口 | 401 |
| 用后厨账号直接调退款接口 | 403 |
| 用前台账号直接调改价接口（页面上没有按钮，用命令调） | 403 |
| （多店时）把请求里的订单编号改成另一家店的订单 | 查不到 |
| 账号停用后，用停用前的会话继续请求 | 401 |
| 对已完成的订单发起退款 | 被拒绝 |
| 两个店长同时对同一单点退款 | 只成功一次 |
| 做完以上操作，去看操作记录 | 每一次成功的敏感操作都有记录，前后值正确 |
| 在日志里搜手机号、密码 | 搜不到明文 |

合规方面，上线前对照上一节的表格，逐项写下：要不要办、谁去办、办到哪一步了。隐私政策逐条对照系统实际收集的字段，有一条对不上就改。系统设计层面怎么把权限放在合适的位置，可以参考 [/guide/system-design](/guide/system-design)。
