## 本章要回答

每月花多少钱；用户翻十倍成本怎么变；老板和运营每天要看什么。

## 示例项目推进到哪

做一张月度成本表和经营看板。

读完这一章，你能列出餐厅后台每个月的钱花在哪里，算出用户涨到十倍时哪几项会跟着涨；也能判断经营看板上的数字是不是老板要看的、算得对不对。

这一章产出两样东西：一张月度成本表，一块经营看板。

## 先列清楚钱花在哪

系统上线以后，每个月都有账单。很多人只记得服务器的钱，其他的散在好几家平台，等哪天信用卡被扣了一笔才想起来。

先把所有花钱的地方列出来，按收费方式分类：

| 项目 | 怎么收费 | 在餐厅后台里是什么 |
|---|---|---|
| 域名 | 按年付 | 后台的网址 |
| HTTPS 证书 | 可以用免费证书，也可以买 | 网址前面的那把锁 |
| 运行环境 | 云服务器按月固定收费；Workers 这类按请求量收费，通常有免费额度 | 接口服务 |
| 数据库 | 托管数据库按套餐，或者按存储和计算用量 | 订单、菜单、顾客 |
| 文件存储和流量 | 按存储量和下载流量 | 菜品图片 |
| 短信 | 按条 | 登录验证码、取餐通知 |
| 支付手续费 | 按交易额的比例，平台直接从每笔里扣 | 第 9 章接的在线支付 |
| AI 接口 | 按调用量，一般按 token 计 | 如果加了智能推荐、自动回复这类功能 |
| 监控、错误收集、备份存储 | 多数有免费档，超出按量收 | 第 8 章加的告警和备份 |
| 人的时间 | 按小时或按月 | 处理告警、对账差异、小修小改 |

最后一行最容易漏，金额也常常最大。系统每个月要有人看告警、处理对账差异、回答甲方的问题。这部分时间要么算进你的维护费，要么就是你白干。维护费怎么谈，见 [第 14 章](/book/ch14)。

表里我没有写价格。各家的价格会变，套餐也经常调整，写在书里很快就过时了。每一项都去官网的价格页或者控制台的账单页查，并且在表里写上查价的日期。

## 用户翻十倍，哪几项跟着涨

老板常问一句话：「以后用的人多了，要多花多少钱？」回答这个问题，先把成本分成三类：

- **固定的**：和用户多少无关。域名、证书、最低一档的服务器。
- **跟着量走的**：每多一单，就多一份钱。支付手续费、短信、AI 调用、图片流量。
- **按台阶涨的**：平时不变，到了某个量就要升一档。服务器配置、数据库套餐。

算法很简单：

> 每月成本 = 固定成本 + 当前台阶的套餐费 + 每单变动成本 × 每月单量

每单变动成本，就是一单要花的手续费、短信、AI 调用和流量加起来。这个数要和每单能赚的钱放在一起看。如果做一单的变动成本快接近做一单的利润了，用户越多亏得越多。

加了 AI 功能的系统，要单独把 AI 调用算一遍：一次调用大概用多少 token，一单会调用几次，按官网价格算出来是多少钱。这一项最容易在用户变多以后突然变大。

成本表可以这样做，每一行都要能说出数字从哪来：

| 项目 | 计费方式 | 现在用量 | 单价（查官网，注明日期） | 现在月费 | 十倍用量 | 十倍月费 | 备注 |
|---|---|---|---|---|---|---|---|
| 域名 | 按年 | 1 个 | | | 1 个 | | 固定 |
| 接口服务 | 按请求量 | 每月多少次请求 | | | ×10 | | 先看是否超出免费额度 |
| 数据库 | 套餐 | 当前存储和用量 | | | | | 看十倍时要不要升档 |
| 图片存储和流量 | 按量 | 每月流量 | | | ×10 | | |
| 短信 | 按条 | 每月条数 | | | ×10 | | |
| 支付手续费 | 按交易额比例 | 每月交易额 | 签约费率 | | ×10 | | 费率看商户平台 |
| 监控和备份 | 按量 | | | | | | |
| 维护人力 | 按小时 | 每月小时数 | | | | | 用户多了问题也多 |

现在的用量从哪里来：云平台的账单页和用量页、短信平台的发送记录、支付平台的账单。这些数据都有，只是散在各处，第一次填要花点时间，以后每月更新一次就行。

还有三件事，能避免账单失控：

- **在云平台上设预算提醒。** 大多数云平台都能设置「本月花费超过多少就发通知」。
- **防止被刷。** 发短信验证码的接口如果没有限流，可能被人用脚本刷，一晚上发出去很多条，钱算在你头上。第 8 章讲的限流就是防这个。
- **密钥不外泄。** AI 接口和云平台的密钥一旦泄露，别人用你的额度，账单也是你的。

给甲方做项目时，我建议各个云服务的账号都用甲方的主体开，甲方自己绑卡付款。你按需要拿操作权限。这样账单清楚，项目结束交接时也不用转移账号。

## 经营看板：老板每天要看什么

餐厅后台的经营首页，面试题要求的是四个数：订单总数、营收、待处理订单数、热销菜品。作为面试题，这样够了。给真实的餐厅用，要先去问老板。

问法很重要。不要问「您想看什么数据」，老板会说「都想看」。要问「您每天早上打开后台，要决定什么事」。然后从决定倒推要看的数：

| 谁看 | 看什么 | 用来决定什么 |
|---|---|---|
| 老板 | 今天营收，和上周同一天比 | 生意是好了还是差了，要不要做活动 |
| 老板 | 订单数和客单价 | 是来的人少了，还是每人花得少了 |
| 老板 | 取消和退款的金额、原因 | 是不是出餐慢、菜做不出来 |
| 老板 | 热销菜和卖不动的菜 | 菜单怎么调整、备多少料 |
| 老板 | 回头客占比 | 要不要做会员和优惠券 |
| 店长 | 待接单、制作超时的订单 | 现在要催谁 |
| 店长 | 各时段订单量 | 怎么排班 |
| 后厨 | 平均出餐时长 | 哪道菜拖慢了出餐 |

客单价就是平均每单多少钱，等于营收除以订单数。

每个数都问一句：看到它变了，你会做什么？答不出来的，先不放。看板上的数字少一点，每个都准，老板才会天天看。

## 每个数都要写清口径

口径就是一个数字具体怎么算。同样叫「今天营收」，可以有好几种算法：

- 算哪些订单？只算已完成的，还是已接单的也算？已取消的肯定不算。
- 接了支付以后，营收是交易额，还是减掉退款以后的实收，还是再减掉手续费以后的到账金额？
- 「今天」从几点算起？数据库里存的时间带时区，看板要按餐厅所在地的时间切日期。服务器在别的时区时，这里很容易错。

这些问题都要和老板定下来，写在看板上每个数字旁边，鼠标放上去就能看到。

陪玩系统在这一点上做过一次统一。订单的报备审核改版以后，规定收益、经营统计和排行榜只统计「审核通过」的订单，支付状态和履约状态不再决定一笔报备算不算数。上线时，历史订单统一设为「草稿」，不会因为以前已经付过钱、已经完成，就被算成审核通过、混进统计。口径写成一条规则，全系统所有统计都从同一处取数，各个页面就不会出现两个对不上的营收。

看板还有一个常见问题：假数据。

陪玩系统的超级管理员后台，早期版本里有演示用的东西：高风险复核页里有一条编出来的复核单，总览页上有几个假的审批和风险处理动作，点了并不会真的处理任何事。我在审查时把它们删了，首页只展示真实的待关注订单和提现事项，平台总览读的是数据库里真实的用户、陪玩师、订单、交易额、提现和操作记录。剩下的问题也列了出来：还不能选时间范围，充值和退款的指标不完整，有些页面上还有写死的指标和临时推算的数。后续要把它们一个个换成有明确来源、有时间口径、没有数据时显示「暂无数据」的真实数据。

让 AI 做看板，它很容易为了让页面好看，填上示例数字或者占位图表。老板看到一个假数字，以为是真的，据此做了决定，比没有这个数还糟。没有数据就显示「暂无数据」，不要显示 0，也不要显示示例。0 表示「算过了，结果是零」，暂无数据表示「还没有可以算的东西」，两者意思不一样。

## 看板怎么验

看板上的数字对不对，不能看 AI 的测试通过就算。我的做法是自己算一遍：

1. 挑一天，把那天的所有订单原始数据导出成表格。
2. 在表格里按定好的口径，手算营收、订单数、客单价、热销菜。
3. 和看板上那一天的数字逐个对比。

挑的那一天要有代表性：有取消的单，有部分退款的单，有跨过午夜的单。再挑一天完全没有订单的，看看看板显示什么。

数据量也要测。演示用的种子数据只有 30 笔订单，看板怎么算都快。真实餐厅营业一年，订单量会大得多。每次打开首页都临时汇总全部订单，页面会越来越慢。在测试环境里造一年量的假订单，打开看板看速度。慢了，就让 AI 改成每天夜里把前一天的数汇总好存起来，看板只读汇总结果。

## 交给 AI 的

成本估算：

```text
帮我做餐厅后台的月度成本表。
1. 根据代码和部署配置，列出系统用到的所有付费服务（运行环境、数据库、存储、短信、支付、AI 接口、监控、备份等），以及各自的计费方式。
2. 每一项告诉我去哪里查当前用量（哪个平台的哪个页面）。
3. 不要编价格。单价一栏留空，旁边写上官网价格页的地址，我自己去查。
4. 按“固定 / 跟着量走 / 按台阶涨”给每一项分类，写出用户涨到十倍时的计算公式。
```

经营看板：

```text
给餐厅后台的经营首页做经营看板。指标和口径如下（贴上和老板确认过的指标表和口径）。
要求：
1. 所有统计从同一个统计模块取数，口径只在一处定义。
2. 日期按餐厅所在时区切分。
3. 每个指标旁边显示口径说明。
4. 不准使用任何示例数据、写死的数字或占位图表。没有数据时显示“暂无数据”。
5. 写测试：用固定的测试订单（含取消、部分退款、跨午夜的订单）断言每个指标的值。
6. 在测试环境生成一年量的订单，测量看板加载时间；超过 2 秒就改为按天预先汇总。
```

## 你要判断和验收的

成本表：

- 每一项付费服务都在表里，没有漏掉的账单。对照上个月信用卡或对公账户的扣款记录核一遍。
- 每一个单价都有查价日期和来源，没有一个是 AI 编的。
- 能回答老板「用户翻十倍要多花多少钱」，并且说得出哪一项涨得最多。
- 每单变动成本小于每单利润。
- 云平台上设好了预算提醒。

经营看板：

- 看板上每个数字，老板都能说出看到它变化后会做什么。
- 每个数字都有写清楚的口径，老板确认过。
- 挑两天手算，和看板一致。
- 没有任何示例数据和写死的数字。
- 没有数据时显示「暂无数据」。
- 用一年量的数据测过，打开速度可以接受。

成本表每月更新一次，看板的口径每次有变动都要重新和老板确认。技术选型会直接影响成本结构，选型时怎么考虑，可以参考 [/guide/tech-stack](/guide/tech-stack)。
