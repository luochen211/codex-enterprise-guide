# 案例：PR 有冲突，也不代表现在就要处理

这是一个协作流程上的案例，不是代码写错了，而是把“发现问题”和“要求别人现在行动”混在了一起。

## 事情是怎么发生的

在 career-ops 的 updater 区域，当时有多条 PR 同时打开，还有刚刚合并的改动。它们修改的地方会互相影响，维护者正在安排合并顺序。

我看到其中一个 PR 的分支落后于 main，于是在跟进评论里提醒贡献者：先同步最新 main，再 rebase，之后才能继续评审。

这个提醒看起来很合理，但它实际上替维护者做了一个我没有权限做的决定：要求作者现在就处理分支。

## 维护者怎么回复

项目维护者 Santifer 很快指出：这个 PR 是 `@briacSck` 的，updater 区域的 PR 还在排队，而且彼此会冲突。现在让作者 rebase，很可能过一会儿还要再做一次。

他给出的核心原则是：

> 不要在 PR 轮到处理之前要求 rebase，轮到它时维护者会通知作者。

他还明确区分了两件事：我列出的技术问题本身不一定错，错的是提醒的时机和提出要求的身份。作者最终得到的结论是：这个 PR 已经排队，现在没有需要做的事。

原始记录可以看 [career-ops PR #2550](https://github.com/santifer/career-ops/pull/2550) 以及维护者的 [回复](https://github.com/santifer/career-ops/pull/2550#issuecomment-5300982817)。

## 这里真正混淆了什么

下面三件事不是一回事：

- PR 分支落后于 main：说明它不是最新基线，不等于作者现在必须操作。
- PR 出现冲突：说明将来合并时可能需要解决冲突，不等于现在就要解决。
- 维护者正在处理这个 PR：这时如果最新 main 已经影响了它，才有理由提出 rebase 或解决冲突的要求。

当多个 PR 修改同一片区域时，过早 rebase 会把维护者的排队问题转嫁给贡献者。前一个 PR 合并以后，后面的 PR 可能还要重新 rebase，作者做的工作就被重复消耗了。

## 下次应该怎么判断

只看到 `Behind`、`Out of date` 或“可能有冲突”，先不要提醒作者。

先确认三个问题：

1. 这个 PR 是否已经排进维护者的评审或合并顺序？
2. 现在要求 rebase 的人，是否真的负责安排这个顺序？
3. 这次同步主线，是否能直接推动当前评审，而不是提前做一次可能失效的准备？

如果答案是否定的，就让 PR 保持排队状态。等维护者准备处理时，再给作者一个明确的动作和原因。

## 复盘

这次错的不是“看到了分支落后”，而是把状态当成了行动授权：

> 发现技术问题，不等于立即要求别人行动；先确认时机、顺序和谁有权提出要求。

这也是为什么《共建指南》里写着：PR 进入处理队列之前，不要因为看到分支落后就统一提醒作者 rebase。
