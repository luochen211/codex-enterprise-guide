# 案例：第二张证明图上传后，第一张为什么不见了？

第二张图上传以后，第一张图不见了。最顺口的判断是“第二次上传把第一次覆盖了”，但这句话比证据走得更快。

## 现象

在完工结算页面中，同一个机位需要上传两张证明图：

- 上传开始证明图：第一次上传成功，页面显示第一张图。
- 上传结束证明图：第二次上传成功，但页面上的第一张图不见了。

![完工结算页面中的两张证明图上传入口](/upload-proof-diagnosis.png)

到这里，日志和页面现象只告诉我们：**第二次操作之后，第一张图在当前页面不可见**。

它还没有告诉我们：第一张图是被删除了、被覆盖了、没有保存，还是只是没有被正确渲染。

## 先写证据边界

### 当前可以确认

1. 第一次上传动作完成后，第一张图曾经可见。
2. 第二次上传动作完成后，第一张图不可见。
3. 两次上传之间存在状态变化。

### 当前不能确认

- 上传接口是否真的删除或覆盖了第一张图。
- 第二次接口返回的数据是否只包含第二张图。
- 前端是否用第二次返回值替换了整个证明图状态。
- 第一张图是否已保存到数据库或对象存储。
- 页面是否只是渲染错了，数据本身仍然存在。

所以这时只能描述现象，不能直接把责任推给上传接口。

## 按日志逐个排查

排查顺序应该沿着数据经过的路径走：

```text
点击上传
  ↓
选择文件与本地状态
  ↓
上传请求 / 响应
  ↓
证明图状态合并
  ↓
保存完工结算
  ↓
数据库 / 对象存储
  ↓
页面重新读取与渲染
```

### 1. 先看第一次上传后的前端状态

记录第一次上传完成后的完整状态，例如：

```text
proofStart = { url: "...", name: "开始证明图" }
proofEnd = null
```

如果第一张图在这里就没有进入 `proofStart`，问题发生在第一次上传或第一次状态写入。

### 2. 再看第二次上传请求和响应

对比第二次上传前后的状态：

```text
第二次上传前：
proofStart = { url: "..." }
proofEnd = null

第二次上传后：
proofStart = ?
proofEnd = { url: "..." }
```

如果第二次响应本身只返回第二张图，但前端把整个证明图对象替换成响应值，优先怀疑**前端状态覆盖**。

如果响应中仍然有两张图，但页面只显示第二张，优先检查**渲染条件、字段映射和列表 key**。

### 3. 检查保存接口的请求体

上传成功不等于业务数据已经保存。要继续看完工结算提交时发送了什么：

```json
{
  "proof_start_url": "第一张图的 URL",
  "proof_end_url": "第二张图的 URL"
}
```

如果提交请求中第一张 URL 已经丢失，问题在提交前的客户端状态链路；如果请求中两张 URL 都存在，继续看服务端日志和数据库写入。

### 4. 最后核对服务端与数据库

只有当服务端日志、数据库记录和重新读取接口都能互相对上，才能判断是否是后端覆盖：

- 服务端收到的字段是否包含两张图。
- 更新 SQL 是否只更新了一个共享字段。
- 数据库记录中是否同时保留两个 URL。
- 刷新页面后的读取响应是否仍然包含两张图。

## 这个现象可能对应的几类问题

| 观察位置 | 更值得怀疑的方向 | 还需要的证据 |
| --- | --- | --- |
| 第二次上传前，第一张状态已丢失 | 页面生命周期或状态初始化 | 第二次上传前的状态日志 |
| 第二次响应后，第一张状态消失 | 前端状态被整体替换 | 请求响应与状态 diff |
| 提交请求缺少第一张 URL | 提交前数据组装错误 | Network 请求体 |
| 提交请求有两张，但数据库只有一张 | 后端字段或更新逻辑覆盖 | 服务端日志、SQL、数据库记录 |
| 数据库有两张，刷新后只显示一张 | 读取映射或渲染问题 | 读取响应、组件 props、渲染条件 |

## 在证据补齐前，结论只能写到这里

在证据没有补齐前，结论应该写成：

> 当前已确认：第二次上传完成后，第一张证明图在页面上不可见。根因尚未确认。下一步对比第一次上传后的状态、第二次上传响应、完工提交请求体、服务端日志和数据库记录，逐层确定是状态覆盖、提交丢失、后端覆盖还是渲染问题。

这样的结论没有假装已经找到根因，却把下一步要补的证据说清楚了。排障的价值不在于最快给问题起名字，而在于让下一次检查能排除一种可能。
