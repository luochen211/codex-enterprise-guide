# 产品形态

在开始用 Codex 做项目之前，先要知道“项目”最后可能交付成什么样。

很多新手一听到做项目，就只想到写代码。但真实业务里的产品形态很多：有的是给用户看的页面，有的是给团队用的后台，有的是跑在微信里的小程序，有的是只提供接口的服务。形态不同，技术栈、验收方式、部署方式和协作重点都会不同。

## 为什么先讲产品形态

产品形态决定了四件事：

| 维度 | 影响 |
| --- | --- |
| 用户入口 | 用户从浏览器、微信、App、桌面软件还是内部系统进入 |
| 技术结构 | 前端、后端、数据库、接口、权限、支付、文件存储等模块如何组合 |
| 交付方式 | 是部署到公网、发布到应用商店、提交小程序审核，还是交付给内部服务器 |
| 验收标准 | 是看页面效果、业务流程、接口稳定性、数据准确性，还是运营后台可用性 |

如果不知道产品形态，就很容易把任务说成“帮我做一个系统”。Codex 可以执行，但它不知道你要的是官网、商城、小程序、管理后台，还是 API 服务。

## 常见产品形态

### 官网和落地页

官网、品牌页、活动页、作品集、课程介绍页，都属于这一类。

它们的核心不是复杂业务逻辑，而是清楚表达信息，并让用户完成一个动作，比如咨询、报名、购买、下载或留下联系方式。

常见技术组合：

- HTML、CSS、JavaScript
- Vue、React、Next.js、Nuxt、VitePress
- 静态托管平台、对象存储、CDN

典型验收标准：

- 页面在手机和电脑上都正常展示。
- 核心按钮、表单、跳转可用。
- 加载速度和基础 SEO 不拖后腿。

### Web 应用

Web 应用是运行在浏览器里的完整工具，比如 CRM、SaaS 后台、项目管理系统、数据看板、在线编辑器。

它比官网更强调登录、权限、数据读写、复杂交互和持续维护。

常见技术组合：

- React、Vue、Svelte 等前端框架
- Node.js、Python、Java、Go 等后端服务
- MySQL、PostgreSQL、Redis、对象存储
- 登录鉴权、接口文档、日志和监控

典型验收标准：

- 用户能完成关键业务流程。
- 数据能正确保存、查询和更新。
- 权限边界清楚，不同角色看到不同功能。
- 构建、测试、部署流程稳定。

### 小程序

小程序通常运行在微信、支付宝、抖音等平台里，适合离用户很近的轻量业务。

它的优势是入口近、传播方便、无需安装；限制是平台规则多，审核、登录、支付、订阅消息、接口域名和包体大小都需要按平台要求处理。

常见技术组合：

- 原生小程序框架
- uni-app、Taro 等跨端框架
- 后端 API、云开发、对象存储
- 微信登录、微信支付、模板消息或订阅消息

典型验收标准：

- 真机预览正常。
- 登录、授权、支付、分享等平台能力可用。
- 接口域名、隐私协议、类目和审核材料完整。
- 页面包体和加载速度符合平台要求。

### 移动 App

移动 App 适合更高频、更复杂或需要系统能力的产品，比如社区、工具、会员系统、设备控制、音视频应用。

它的门槛通常高于小程序，因为涉及 iOS、Android、应用商店审核、版本升级、推送、崩溃监控等问题。

常见技术组合：

- Swift、Kotlin 等原生开发
- Flutter、React Native 等跨端开发
- 后端 API、推送服务、埋点和崩溃监控

典型验收标准：

- 在主流机型和系统版本上稳定运行。
- 登录、支付、推送、权限申请符合平台规则。
- 有版本发布、灰度、回滚和问题追踪机制。

### 管理后台

管理后台是给运营、客服、财务、管理员或内部员工使用的系统。

它不一定漂亮，但必须清楚、稳定、可审计。后台最常见的问题不是页面难看，而是权限混乱、数据误操作、缺少日志和导出能力。

常见技术组合：

- Vue、React、Ant Design、Element Plus
- 后端管理接口
- 角色权限、操作日志、数据导入导出

典型验收标准：

- 列表、搜索、筛选、分页、详情、编辑、删除等基础操作完整。
- 危险操作有确认和权限控制。
- 关键操作有日志，必要数据可以导出。

### API 服务

有些项目没有直接面对用户的界面，而是提供接口给网站、小程序、App 或第三方系统调用。

API 服务的核心是稳定、清晰、安全和可扩展。

常见技术组合：

- REST、GraphQL、WebSocket
- OpenAPI 文档
- 数据库、缓存、队列、鉴权、限流
- 日志、监控、告警

典型验收标准：

- 接口字段、错误码和鉴权规则清楚。
- 有可运行的接口文档或调试示例。
- 异常、超时、重复提交和权限问题被处理。

### 自动化脚本和内部工具

不是所有项目都需要做成完整产品。有些任务只需要一个脚本、插件、命令行工具或内部页面。

这类形态适合解决重复劳动，比如批量处理文件、生成报告、同步数据、检查链接、自动部署。

常见技术组合：

- Shell、Node.js、Python
- GitHub Actions
- 内部管理页面或命令行工具

典型验收标准：

- 输入输出清楚。
- 失败时有错误提示。
- 可以重复执行，不会破坏已有数据。

## 如何向 Codex 描述产品形态

给 Codex 分配任务时，可以先补上这段上下文：

```text
这个项目的目标形态是一个微信小程序，用户可以浏览课程、提交报名信息，并通过后台查看报名列表。

请先按“小程序前端 + 后端 API + 管理后台”的结构理解项目，不要把它当成普通官网。
本次只完成报名表单页面和提交接口，不处理支付。
验收标准是：真机预览页面正常，表单校验可用，提交后后台能看到记录。
```

你也可以用更短的模板：

```text
产品形态：
目标用户：
核心场景：
需要交付的端：
暂时不做的范围：
验收方式：
```

## 新手先记住一句话

不要一上来就问“用什么技术栈”。

先问：这个项目最终要以什么产品形态被谁使用？

产品形态清楚了，Codex 才能帮你把任务拆得更准，代码写得更贴近真实交付，验证也不会只停留在“能跑起来”。
