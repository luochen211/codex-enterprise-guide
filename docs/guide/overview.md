# 项目总览

Codex Enterprise Guide 是一个面向真实工作流的 Codex 实践项目。

它的目标不是证明 Codex 很强，而是回答更具体的问题：

- 一个新手如何稳定完成第一个任务？
- 一个开发者如何让 Codex 进入已有仓库？
- 一个团队如何设定规则、权限、验收和复盘？
- 一个公开项目如何从本地页面变成可持续发布的网站？

## 核心原则

### 先判断产品形态

做项目前要先判断最终交付物是什么形态：官网、Web 应用、小程序、移动 App、管理后台、API 服务，还是自动化脚本。

形态不同，入口、技术结构、部署方式和验收标准都不同。你可以先阅读[产品形态](/guide/product-forms)，再进入具体路线。

### 再说明技术栈

技术栈说明项目由哪些层组成：前端、小程序端、后端、数据库、文件存储、部署平台、CI/CD 和监控。

技术栈越清楚，Codex 越容易判断应该读哪些文件、运行哪些命令、遵守哪些框架约定。你可以阅读[技术栈](/guide/tech-stack)，建立项目结构的基本地图。

### 代码要适合协作

对 AI 友好的代码，本质上也是对人友好的代码：高内聚、低耦合、单一职责。

当模块边界清楚、函数职责单一、依赖关系简单时，Codex 更容易小步修改、准确验证，并说明影响范围。你可以阅读[对 AI 友好的代码](/guide/ai-friendly-code)，理解代码组织为什么会影响 AI 协作质量。

### 任务要可执行

好的 Codex 任务需要有明确上下文、边界、验收标准和验证方式。

不要只说“帮我优化项目”。更好的说法是：

```text
请先阅读项目结构和 README，理解当前文档站的技术栈。
然后新增一篇服务器部署教程，要求能被 VitePress 构建通过。
最后运行构建命令，并总结修改文件和验证结果。
```

### 结果要可验证

每次改动都要回答三件事：

| 问题 | 示例 |
| --- | --- |
| 改了什么 | 新增部署章节和 CI workflow |
| 怎么验证 | `npm run build`、GitHub Actions 成功 |
| 还有什么风险 | Pages 缓存、域名未配置、内容还需要补图 |

### 经验要可沉淀

当一个任务重复出现，就应该沉淀成模板、脚本、Skill 或团队规范。

## 项目边界

这个项目优先做四类内容：

1. 产品形态、技术栈、代码组织与基础认知。
2. Codex 入门与任务设计。
3. 工程项目协作与验证。
4. 服务器、部署、CI/CD 与上线维护。
5. 真实案例复盘。

暂时不做模型评测、不做工具横向榜单，也不把内容写成泛泛的 AI 新闻。
