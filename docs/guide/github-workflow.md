# GitHub 协作基础：从仓库到 worktree

很多 Git 事故来自身份混乱：远端主线、本地目录、功能分支和 PR 被当成了同一件事。先把它们分开，后面的 worktree 事故才看得懂。

你可以先记住一句话：

> GitHub 负责保存和审核远端代码，branch 负责区分不同路线，worktree 负责在电脑里提供不同的工作目录。

## GitHub 上的几个基本东西

### 仓库

仓库就是一个项目的远端家。代码、提交、分支、Issue、PR 和 GitHub Actions，通常都围绕这个仓库展开。

### main

main 是默认主线。它通常代表大家认可的、准备继续往前走的那条代码路线。

GitHub 上的 main 可能已经向前走了很久，而电脑里的本地 main 还停在旧提交。判断主线时，要比较它们实际指向的提交，不能只看分支名字。

### 分支

分支就是从某个时间点分出来的一条代码路线。

功能分支通常用来做一项新功能，例如 feat/issue-19-ops-config；修复分支通常用来解决一个问题，例如 fix/order-500-datetime-serialization。

分支名字只是提示，不是证据。真正要确认它是什么，还是要看它实际指向的提交，以及它和 main 的关系。

### PR

PR 是把一条分支的改动拿出来，请别人审核、跑检查，最后决定要不要合进 main。

PR 记录的是“这批改动能不能进入主线”。本地工作目录是否安全、功能分支是否追上最新 main，还要分别检查。

### 分支保护

分支保护是 GitHub 帮你守住 main 的规则。可以要求改 main 必须经过 PR、审核和检查，也可以禁止直接修改或强行覆盖主线。

公开仓库可以在 GitHub Free 使用分支保护。

个人私有仓库如果还是 GitHub Free，不能使用这类完整保护。想让 GitHub 强制要求 PR、审核和检查，需要开通 GitHub Pro，目前是每月 4 美元。组织名下的私有仓库，则要看组织的 Team 或 Enterprise 计划。

没有这层保护时，只能靠团队约定“不直接改 main”，GitHub 不会替你拦住误操作。

## worktree 到底是什么

worktree 是 Git 在本地提供的多工作目录能力，GitHub 页面里看不到这些目录。

普通情况下，一个项目目录一次只能切一个分支。worktree 可以让你同时拥有多个目录：一个目录看 main，一个目录做功能，一个目录处理修复，互相不需要来回切换。

它解决的是本地隔离问题：

- 不用为了处理另一个任务反复切分支。
- 一个目录有未提交改动时，不会轻易影响另一个任务。
- 多个任务可以并行开发和测试。

但 worktree 也带来一个风险：目录多了以后，人很容易只看目录名字，不看它实际对应的分支。

目录名只是人为写下的标签。`issue-21-main` 里面可能检出旧 main，也可能是功能分支，还可能留着没提交的改动。

## DAG 又是什么

DAG 是任务之间的依赖关系图。

比如：

- 先完成数据库调整。
- 再做后端接口。
- 最后做前端页面。

DAG 解决的是“哪个任务先做、哪个任务依赖哪个任务”。它不保存代码，也不替代 branch、PR 或 worktree。

可以这样分工：

| 东西 | 它解决的问题 |
| --- | --- |
| GitHub 仓库 | 代码和协作记录放在哪里 |
| main | 哪条路线是默认主线 |
| branch | 这一批代码属于哪条路线 |
| PR | 这批代码能不能合进主线 |
| 分支保护 | 谁也不能随便改主线 |
| worktree | 这条分支在电脑哪个目录里工作 |
| DAG | 多个任务之间谁依赖谁 |

## 一次正常的协作过程

先确认 GitHub 上最新的 main，再从它开始做任务。

任务有自己的分支，需要并行开发时，再给这个分支安排独立 worktree。开发完成后，把代码推到 GitHub，创建 PR，等待检查和审核。

PR 合并之后，才说明这批代码进入了主线。对应的 worktree 可以在确认没有未提交改动、材料已经交接之后删除。

这里有一个顺序不能反：

> 先确认主线，再确认分支；先保护工作目录，再开始恢复；最后才清理 worktree。

## 一个很容易做错的 PR 提醒

PR 显示分支落后或冲突时，先看它有没有排进维护者的处理顺序，以及谁负责安排合并，再决定是否通知作者 rebase。

如果多个 PR 正在改同一片区域，提前 rebase 可能在前一个 PR 合并后立刻失效，作者还得重复做一遍。没有负责合并顺序的人授权，就不要看到 `Behind` 就提醒作者处理。

真实案例见：[PR 有冲突，也不代表现在就要处理](/cases/pr-rebase-timing-incident)。
