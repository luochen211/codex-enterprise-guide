# 从业务流转到系统设计

系统设计不是先画页面，也不是先决定使用 React、Vue 还是小程序。它首先要回答两个问题：

1. 业务现在实际上是怎么流转的？
2. 系统怎样介入，才能让这个流程更高效、更少出错、更容易追责？

如果这两个问题没有弄清楚，页面越早开始做，越容易把现实中的混乱直接固化成新的系统流程。

## 一、先还原业务现实

需求文档通常只描述“希望系统有什么功能”，不一定描述了业务每天真实如何工作。系统设计的第一步，是把当前状态（As-Is）还原出来。

至少要查清楚这些问题：

| 要素 | 要回答的问题 |
| --- | --- |
| 参与者 | 谁提出需求、谁做决定、谁执行、谁检查结果？ |
| 触发条件 | 什么事情发生后，流程开始或进入下一步？ |
| 输入信息 | 决策时依赖哪些表格、聊天记录、订单、库存或外部数据？ |
| 判断规则 | 谁根据什么条件决定通过、分配、暂停或重做？ |
| 交接过程 | 信息从谁传给谁，在哪个环节最容易丢失？ |
| 异常情况 | 临时变更、资源不足、时间冲突、重复提交时怎么处理？ |
| 最终结果 | 业务完成后，留下什么记录，谁需要看到？ |

不要只问“你想要什么页面”，还要观察：

- 大家现在用什么工具协作，例如群聊、表格、电话或纸面记录。
- 一个真实案例从开始到结束经过了哪些人。
- 哪些步骤依赖某个熟悉业务的人临时判断。
- 出错后是谁发现问题，又是谁知道如何修复。
- 哪些规则写在文档里，哪些规则只存在于团队经验中。

只有把这些事实画出来，才能分清“系统缺功能”和“业务本身还没有形成统一规则”。

## 二、效率不只是少点几次按钮

系统效率至少包括五个方面：

- 减少重复沟通：同一条信息不需要在群聊、表格和系统之间重复抄写。
- 减少误操作：不让不拥有决策权的人直接修改关键数据。
- 减少等待：把可以自动判断、分配、通知的步骤交给系统。
- 保持一致：所有角色读取同一个事实来源，而不是各自保存一份版本。
- 便于追溯：出现问题时能知道谁在什么时候改了什么，以及为什么改。

因此，“效率变高”不等于给所有人更多按钮。很多时候，效率更高的设计是：让真正负责的人集中操作，让其他人快速查看，让系统自动执行确定性的规则。

## 三、先设计分工，再设计页面

一个可落地的系统，通常要把工作分成三类：

| 工作类型 | 适合由谁完成 | 典型内容 |
| --- | --- | --- |
| 业务决策 | 负责统筹的人 | 排班、审批、资源分配、特殊例外 |
| 业务执行 | 一线工作人员 | 接收任务、完成工作、回填结果 |
| 确定性计算 | 系统自动完成 | 校验、排序、派单、扣减、提醒、统计 |

这不是把所有事情都交给管理员，也不是把所有编辑权都开放给一线人员，而是把决策权放在最了解全局的位置，把重复计算交给系统，把执行动作留给实际工作的人。

权限设计必须和这个分工一致：

- 页面上不显示不该操作的按钮。
- 接口层也必须拒绝越权写入，不能只依赖前端隐藏。
- 关键变更要有操作人、时间、原因和变更前后的内容。
- 涉及已有订单、库存或资源占用时，系统要先提示冲突，再允许负责人处理。

## 四、系统设计的正确顺序

推荐按下面的顺序推进：

### 1. 绘制当前流程

用时间线或泳道图描述真实流程。泳道至少按角色分开，并标出每次交接、判断和异常分支。

### 2. 找出低效点和风险点

不要只列“没有某个功能”，还要说明后果：重复录入、等待确认、责任不清、数据不一致，还是出错后无法恢复。

### 3. 设计目标流程

明确哪些步骤保留人工判断，哪些步骤改成系统规则，哪些信息只需要展示，哪些信息必须由指定角色维护。

### 4. 确定角色和权限

先决定谁能看、谁能改、谁能发布、谁能撤回，再设计页面。权限是业务设计的一部分，不是上线前才补的技术细节。

### 5. 设计数据和状态

为核心对象定义状态、来源、负责人、变更记录和有效时间。涉及排班、订单、库存等资源时，还要区分“计划状态”和“已发生事实”。

### 6. 设计异常和恢复

提前回答：已有任务时能不能改？改动会不会影响后续流程？冲突由谁处理？能不能撤回？系统如何通知受影响的人？

### 7. 最后设计页面和接口

页面应该服务于已经确定的业务分工。接口应该表达业务动作和权限边界，而不是简单把数据库字段全部暴露给前端。

### 8. 用真实场景验收

至少准备正常流程、临时变更、资源不足、时间冲突、重复提交和越权操作等场景。能通过这些场景，才说明设计真的覆盖了业务。

## 五、排班系统案例：从个人编辑改成统一排班

以团队排班为例，最容易犯的错误是：看到“每个人都有自己的档期”，就直接做一个“修图师档期设置”页面，让每个人自己修改。

### 当前容易出现的问题

现实中，团队往往先聚在一起讨论整个月怎么排班。若系统上线后允许每个人直接修改自己的日期和时段，就会出现：

- 一个人把周日改成休息，却没有同步调整其他日期。
- 修改后影响了已经安排的任务，但本人不知道如何处理。
- 不同成员看到的排班不是同一版本。
- 系统只提示“保存成功”，却没有记录业务原因。

这不是输入框设计得不够好，而是操作权放错了位置。

### 目标流程

更合理的流程是：

```text
团队讨论排班
    -> 排班负责人在统一工作台调整
    -> 系统校验人数、时间冲突和已有任务
    -> 发布一份生效中的排班
    -> 修图师在小程序查看自己的排班
    -> 客户下单后，系统按排班和精力规则自动分配
    -> 临时变化仍由负责人统一调整并留下记录
```

### 修图师端应该做什么

修图师端不是“设置档期”，而是“我的排班”：

- 查看月度日历和每天的开放状态。
- 点击日期后查看上午、下午、晚上的状态。
- 查看自己的可承接精力值、已消耗值和剩余值。
- 点击展开“精力值规则说明”，查看不同业务类别的消耗分值。
- 看到排班最后更新时间和调整提示。

这个页面不需要个人直接修改排班、提交保存或填写业务类别分值。临时需要调整时，沿用团队已有的沟通方式通知负责人，由负责人统一处理。

### 排班工作台应该做什么

管理端应该提供面向团队的排班工作台，而不是只能查看某个人的精力值：

- 行展示人员，列展示日期，每天拆成上午、下午、晚上。
- 支持批量设置接单、休息和暂停状态。
- 支持交换两个日期的排班，适合处理临时调班。
- 支持设置默认精力值和指定日期、时段的覆盖值。
- 保存前展示影响范围，并提示已有订单或时间冲突。
- 发布后记录操作人、时间、原因和版本。

### 后端必须保证什么

不能只把小程序上的按钮隐藏起来。后端还必须保证：

- 修图师可以读取自己的排班，但不能直接写入排班数据。
- 排班负责人才能修改和发布团队排班。
- 排班变更以一次完整操作提交，避免周日已改、周二未改的半成品状态。
- 已有任务受到影响时，返回明确的冲突信息。
- 派单只读取已生效的排班版本，并保存派单时使用的精力值快照。

## 六、常见的错误设计

### 先画页面，再补业务规则

结果通常是页面看起来完整，但没人知道谁负责操作，也没有办法处理异常。

### 把所有人都当成管理员

“每个人都可以改自己的数据”看起来灵活，实际会造成数据版本混乱和责任不清。

### 只做前端权限

隐藏按钮不能阻止用户直接调用接口。写权限必须在服务端校验。

### 用一个“保存”覆盖所有业务动作

排班发布、临时调班、取消发布和规则调整的风险不同，应该让系统能区分动作、记录原因并执行不同校验。

### 只处理正常流程

企业系统的价值往往体现在异常流程：临时请假、任务已经分配、资源不足、人员冲突和误操作恢复。

## 七、开始设计前的最小问题清单

可以用下面这份清单启动任何一个新系统：

```text
产品形态：它是小程序、Web 应用、管理后台、API 还是组合系统？
目标用户：谁使用？谁负责决策？谁只需要查看结果？
当前流程：业务现在从哪里开始，经过哪些人，最后如何结束？
核心问题：当前最浪费时间、最容易出错、最难追责的环节是什么？
目标流程：哪些步骤保留人工，哪些步骤交给系统自动完成？
权限边界：谁能查看、编辑、发布、撤回和处理例外？
核心数据：系统要保存哪些事实、状态、版本和变更记录？
异常处理：已有任务、时间冲突、重复提交和误操作如何处理？
验收方式：用哪些真实场景证明系统真的改善了业务？
暂不做什么：哪些功能不属于本轮范围，避免设计不断膨胀？
```

当这些问题有了答案，页面、技术栈和开发任务才有了可靠的上下文。Codex 这时才能准确判断应该读哪些文件、修改哪些模块、运行哪些验证，并把一次项目经验沉淀成下一次可以复用的系统设计方法。
